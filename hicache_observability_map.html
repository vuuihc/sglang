关键 CLI 参数

参数作用
--enable-hierarchical-cache启用 L1 GPU + L2 host + 可选 L3 storage 的 HiCache 路径。
--hicache-ratio / --hicache-size控制 host KV pool 大小。
--hicache-write-policywrite_back / write_through / selective，影响 L1→L2 写回时机。
--hicache-io-backendkernel / direct / kernel_ascend，影响 CPU↔GPU copy 实现。
--hicache-mem-layouthost memory layout：layer/page/head 等。
--hicache-storage-backend启用 L3 storage backend，和 storage metrics / mooncake trace 更相关。
--enable-metrics启用 Prometheus metrics collector；#26974 的 L1/L2 series 也受它控制。
--enable-trace启用 OpenTelemetry trace，和 Prometheus metrics 是两套观测系统。

2. #26974 / follow-up 增加的 metric 范围和值

设计目标：把每次 HiCache L1↔L2 搬运从“异步 ACK 完成”升级为“可统计的 transfer event”：方向、blocks、bytes、duration、bandwidth。

覆盖范围

方向路径含义
direction="offload" L1 GPU → L2 host write-back / write-through，把 device KV block 备份到 host。
direction="onboard" L2 host → L1 GPU load-back，把 evicted prefix 对应 KV block 重新搬回 GPU。

计时边界

write path
start_writing() 创建 Event(enable_timing=True) 的 start/finish，围住 L1→L2 copy stream。
load path
LayerLoadingEvent.start_event 和最后一层 load_event 使用 enable_timing=True，作为 L2→L1 elapsed-time pair。
ACK complete
loading_check() / writing_check() 在 ACK 完成后调用 record_l1_l2_transfer_complete()。
fallback
如果 backend 不支持 elapsed_time()，仍可退到 host wall-clock；但 CUDA 正常路径应走 timing event。

为什么它比旧 load_back_duration_seconds 更“完整”？ 它不是只看 load-back，而是看 L1/L2 双向数据运动；不仅有 duration，还有 blocks、bytes、bandwidth 和 rank/backend labels。 对诊断“搬得多”还是“带宽差”更直接。
为什么它不应完全替代旧 metric？ 新 metric 是 transfer-level；旧 load_back_duration_seconds 可以被重新定义为 cache-visible latency， 包括排队、调度、ACK 被 poll 的等待。这样两者才不重复。

3. 当前项目 trace / metrics 覆盖范围

OpenTelemetry trace

通过 --enable-trace 打开，--trace-modules 目前支持 request 和 mooncake，输出到 --otlp-traces-endpoint。

trace 以 request/root span 为中心，覆盖 API/tokenizer、DP dispatch、scheduler queue、prefill/decode forward、spec draft/verify 等。

Prometheus metrics

通过 --enable-metrics 打开。已有 request/scheduler/cache/storage metrics； #26974 新增 L1/L2 transfer metrics。

metrics 适合 dashboard / alert / aggregate；trace 适合单请求链路和跨线程/跨服务关联。

Profiler / Chrome trace

Torch profiler、ROCm RPD 和 trace merger 生成的是 profiling trace， 主要用于性能剖析，不等同于 OpenTelemetry request trace。

观测面 当前覆盖 HiCache 相关性 主要缺口
Request trace request start/finish、tokenize、API dispatch、DP dispatch、waiting、prefill/decode forward、decode loop、schedule events、speculative draft/verify。 能看到请求级等待/forward，但不直接知道 L1/L2 搬了多少 bytes。 没有把 HiCache load-back/offload 作为 per-request span 显式挂上去。
Mooncake trace trace_modules=mooncake 下覆盖 Mooncake send/transfer slice。 更偏 L3/跨节点 KV transfer；和 HiCache storage backend 有交集。 非 Mooncake storage backend 的 tracing 覆盖不对称。
Storage metrics prefetch/backup pages、bandwidth、tokens 等，backend 包括 Mooncake/HF3FS 等。 覆盖 L2↔L3，不覆盖 L1↔L2 DMA。 更适合 aggregate，不提供单请求 trace 链接。
L1/L2 transfer metrics #26974 新增 offload/onboard blocks、bytes、duration histogram。 正中 HiCache CPU↔GPU transfer；修 enable_timing=True 后可算真实带宽。 仍是 aggregate metrics；不是 request trace span。
旧 load_back metric sglang:load_back_duration_seconds 当前 main 在 load_back() 中用 CPU wall-clock 包 dispatch。 现在语义偏“调度/dispatch 开销”，不是 DMA，也不是完整 cache-visible latency。 可以改造成 cache-level load-back latency，和新 L1/L2 transfer metric 拉开边界。

推荐的最终语义分工

DMA health
hicache_l1_l2_transfer_duration_us + bytes/blocks：纯 transfer 层，回答“带宽健康吗”。
Cache impact
load_back_duration_seconds：cache 可见的 load-back latency，回答“请求被 load-back 拖了多久”。
Request story
OpenTelemetry request trace：回答“这个请求在哪个阶段慢”，未来可补 HiCache span。

如果后续做你的 PR

建议不要再和 #26974 争“旧 metric 也测 DMA”。更科学的 follow-up 是：

load_back_duration_seconds = cache-visible load-back latency

也就是从 load_back() 记录开始时间，到 loading_check() 消费 ACK 时 observe。 这样它自然包含排队、调度、DMA 和 ACK polling delay，和 L1/L2 transfer metrics 形成互补。

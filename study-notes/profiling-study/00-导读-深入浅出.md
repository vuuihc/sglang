## 1. 先搞清楚：我们在干什么

**目标**：找到 sglang 推理引擎中可以优化的性能瓶颈，最好是"改几行代码就能提个 PR"的那种。

**方法**：用 GPU profiler（torch profiler）抓取推理过程中的时间线（trace），分析 GPU 时间花在哪、CPU 时间花在哪、哪里有"气泡"（GPU 空闲等 CPU）。

**结论（剧透）**：模型前向路径已经被优化得很充分了，没有"躺在地上的 1 行 quick-win"。真正的优化空间在真实 serving 的 host 侧调度逻辑（`scheduler` / `tokenizer`），而且连那里都有人在做了（PR #24734）。

## 2. 硬件和模型：为什么选 H20 + Qwen3-8B

### 2.1 H20 是一张"畸形"卡

先看这张对比表（来自 [01-环境搭建.md](01-环境搭建.md)）：

| 卡 | 架构 | fp16 算力 | 显存带宽 | 显存 |
|---|---|---|---|---|
| RTX 4090D | sm89 | 中 | ~1 TB/s | 24GB |
| A100 | sm80 | 中高 | ~2 TB/s | 80GB |
| **H20** | **sm90** | **极低(~148T)** | **~4 TB/s(满血)** | **96GB** |
| H800 | sm90 | 高(~990T) | ~3.4 TB/s | 80GB |

H20 的特殊之处：**算力被砍得很惨，但显存带宽是满血的**。这意味着：

- **decode 阶段（memory-bound）是 H20 的甜点**——decode 每次只算 1 个 token，瓶颈在"把模型权重从显存搬到计算单元"的速度（带宽），而不是算力。H20 带宽高，适合 decode。
- **算力弱反而让 host 开销更显眼**——GPU 算得慢，CPU 调度的时间占比就相对更大，更容易在 trace 里观察到。

另外，H20 是 sm90 架构（Hopper），这是 sglang 最新版（0.5.13.post1）的最低要求——`sglang-kernel` 预编译包只编了 sm90 和 sm100，4090D（sm89）和 A100（sm80）装不上。

### 2.2 Qwen3-8B（bf16）

选 8B 模型是因为它够小、能在单卡上跑各种 batch size 的实验。bf16 精度是当前主流推理精度。

## 3. 两种 Profiling 入口：microbench vs 真实 serving

整个实验用了两种抓 trace 的方式，对应两个脚本：

### 3.1 离线 microbench：[`scripts/profile_decode_bottlenecks.sh`](../../scripts/profile_decode_bottlenecks.sh)

```bash
python -m sglang.bench_one_batch \
  --model-path Qwen/Qwen3-8B \
  --batch-size 1 8 32 64 \
  --input-len 512 --output-len 64 \
  --profile --profile-stage decode --profile-steps 5
```

`bench_one_batch` 是 sglang 自带的**纯模型前向**基准测试。它做的事情非常简单：

1. 加载模型权重到 GPU
2. 构造一批随机输入（input_len=512 个 token）
3. 跑一遍 prefill（把 512 个 token 一次性编码）
4. 然后逐 token 做 decode（生成 64 个 token），抓中间几步的 trace

**优点**：干净、可复现、没有网络/调度/排队等干扰。适合学习读 trace。
**缺点**：它**不经过 scheduler 和 tokenizer**——真实 serving 中那些 per-request 的 Python 逻辑（KV cache 分配、penalizer、sampling）全都没触发。所以它只能分析模型前向路径，分析不了 host 侧调度开销。

### 3.2 真实 serving：[`scripts/profile_serving_scheduler.sh`](../../scripts/profile_serving_scheduler.sh)

```bash
# 1. 起 server
python -m sglang.launch_server --model-path Qwen/Qwen3-8B --port 30000

# 2. 打负载 + 抓 trace
python -m sglang.bench_serving \
  --backend sglang --host 127.0.0.1 --port 30000 \
  --num-prompts 300 --max-concurrency 32 \
  --profile --profile-steps 20
```

这个脚本起一个真实的 sglang server，然后用 `bench_serving` 发送 300 个并发请求，同时通过 `/start_profile` + `/stop_profile` API 抓取 **scheduler 进程**的 trace。

**优点**：能抓到 microbench 抓不到的 host 侧开销——scheduler 的 Python 调用树、KV cache 分配、tokenizer/detokenizer。
**缺点**：有网络和排队噪声，trace 更复杂。

> 实验一到四用的是 microbench，实验五用的是 serving。

## 4. 核心概念速成：读懂 trace 前必须知道的几个词

在看具体实验数据之前，先建立几个关键概念。

### 4.1 Prefill vs Decode

LLM 推理分两个阶段：

- **Prefill（预填充）**：把用户输入的所有 token 一次性喂给模型。这是 **compute-bound**（算力密集型）——GPU 算力打满，kernel 排得密不透风。
- **Decode（逐 token 生成）**：每次只生成 1 个 token，但要把之前所有 token 的 KV cache 都读一遍。这是 **memory-bandwidth-bound**（带宽密集型）——GPU 大部分时间在等数据从显存搬过来。

小 batch decode 还有一个额外瓶颈：**host launch overhead**——CPU 要逐个发射几百个 GPU kernel，每个发射都有几微秒的延迟，累积起来 GPU 就大量空等。这就是 trace 里的"气泡"。

### 4.2 Host-bound vs Compute-bound

- **Host-bound**：GPU 在等 CPU 干活（发射 kernel、分配内存、做 Python 逻辑）。trace 里表现为 GPU 泳道有大量空隙（气泡）。
- **Compute-bound**：GPU 一直在算，CPU 跟不上也无所谓。trace 里 GPU 泳道排得满满的。

**sglang 那些小而美的 perf PR，大多在小 batch decode 的气泡里。**

### 4.3 Cuda Graph

正常情况下，每做一次 forward，CPU 要逐个发射几百个 GPU kernel：

```
CPU: launch(kernel1) → launch(kernel2) → launch(kernel3) → ...
GPU: [kernel1][kernel2][kernel3]...
```

每个 `launch()` 调用有 ~5-10μs 的延迟。几百个 kernel 累积起来就是几毫秒——GPU 在这些间隙里是空闲的。

**Cuda Graph 的做法**：把整个 forward 的几百个 kernel 调用"录"成一张图，之后每次 forward 只需要一次 `cudaGraphLaunch`，CPU 发射开销从几百次变成 1 次。

```
CPU: cudaGraphLaunch(graph)
GPU: [kernel1][kernel2][kernel3]...  ← 没有间隙了
```

**代价**：录成图后，trace 里所有 kernel 的"来源"都指向 `cudaGraphLaunch` 那一行，你看不出每个 kernel 是哪行 Python 代码发的。这就是为什么需要"关图版 trace"做源码归因。

### 4.4 Trace 怎么看

把 `.trace.json.gz` 拖进 https://ui.perfetto.dev（无需解压）：

- **上方泳道**：CPU 线程（Python 调用栈、kernel launch）
- **下方泳道**：CUDA stream（GPU kernel 执行）

**核心技巧**：看 GPU 泳道里两个 kernel 之间有没有空隙。空隙 = 气泡 = GPU 在等 CPU = host-bound。

### 4.5 三张自动分析表

`analyze_llm_torch_profile.py` 脚本自动吐出三张表：

| 表 | 含义 |
|---|---|
| **Kernel 表** | GPU 时间花在哪些 kernel 上，每个 kernel 映射回 Python 代码位置 |
| **Overlap 表** | GPU 本可靠重叠隐藏的气泡（单 trace 模式偏保守，常为空） |
| **Fuse 表** | 可以合并成一个 kernel 的候选，对照已知/在途的融合 PR |

## 5. 实验一：batch 扫描——看 host→compute 的转折点

### 5.1 实验对象

用 `bench_one_batch` 在 **cuda graph 开**的情况下，扫 batch=1, 8, 32, 64，抓 decode 阶段的 trace。

### 5.2 数据

| batch | 每步时延 | 吞吐 | 每 token 时延 |
|---|---|---|---|
| 1 | 6.08 ms | 164 tok/s | 6.08 ms |
| 8 | 6.65 ms | 1204 tok/s | 0.83 ms |
| 32 | 8.91 ms | 3590 tok/s | 0.28 ms |
| 64 | 13.39 ms | 4780 tok/s | 0.21 ms |

### 5.3 怎么读

**关键观察：batch 从 1 到 8，工作量翻了 8 倍，但每步时延几乎没变（6.08→6.65ms，只涨了 9%）。**

这意味着什么？batch=1 时，GPU 大部分时间不是在"算"，而是在做跟 batch 大小无关的"固定开销"——比如等 CPU 发射 kernel、等数据从显存搬过来。这 6.08ms 里，真正用于计算的只有一小部分。

到 batch=32 时，时延开始明显上涨（8.91ms），说明计算量终于大到足以主导整步时间了——这就是 **host-bound → compute-bound 的转折点**。

**通俗类比**：你开一家奶茶店。
- batch=1：就一个顾客，你做奶茶只要 30 秒，但收钱、拿杯子、洗机器花了 5 分钟——大部分时间在"固定开销"上。
- batch=32：32 个顾客一起来，你做奶茶要 20 分钟，收钱拿杯子还是 5 分钟——固定开销被摊薄了，做奶茶（计算）成了主导。

### 5.4 意义

这个实验告诉我们：**小 batch decode 的优化空间在"固定开销"上，不在计算本身。** 如果能把固定开销砍掉，小 batch 的吞吐能大幅提升。这就是 cuda graph 要做的事（见实验三）。

## 6. 实验二：batch=1 的 GPU 利用率——82% 时间在 GEMM

### 6.1 实验对象

取实验一中 batch=1 的 trace（cuda graph 开），用 `analyze_llm_torch_profile.py` 分析 kernel 表。

原始数据在 [`.contribution-scan/analysis/triage_dense_batch1.txt`](../../.contribution-scan/analysis/triage_dense_batch1.txt)。

### 6.2 数据

Kernel 表的核心行（decode 阶段，5 步累计）：

| Kernel | GPU 时间 | 占比 | 类别 |
|---|---|---|---|
| `nvjet_*` GEMM（4 个变体） | 22.50 ms | 80.3% | 矩阵乘 |
| FlashAttn (sm90) | 1.53 ms | 5.5% | 注意力 |
| Fused Add+RMSNorm | 0.96 ms | 3.4% | 归一化 |
| cublasLt splitK reduce | 0.81 ms | 2.9% | 矩阵乘辅助 |
| act_and_mul | 0.36 ms | 1.3% | 激活函数 |
| fused_qknorm | 0.35 ms | 1.2% | QK 归一化 |
| fused_rope | 0.30 ms | 1.1% | 位置编码 |

**GPU 真忙的 kernel 累计 ~28ms / 5 步 = 5.6ms/步。墙上时间是 6.08ms/步。GPU 利用率 = 5.6/6.08 ≈ 92%。**

### 6.3 怎么读

**82% 的 GPU 时间在 `nvjet_*` GEMM 上。** `nvjet` 是 NVIDIA cuBLAS 的启发式矩阵乘 kernel——就是做 `y = xW` 这种线性变换。Qwen3-8B 有 32 层 Transformer，每层有 Q/K/V/O 四个投影矩阵 + 两个 FFN 矩阵，decode 时每个 token 都要过一遍，所以 GEMM 占了绝对大头。

**这个 82% 是硬件墙，不是软件问题。** H20 的 fp16 算力只有 ~148 TFLOPS（被 NVIDIA 故意砍的），GEMM 算得慢是物理限制，换什么代码都快不了。唯一相关的优化是 PR #22392（用 CUTLASS 替换 nvjet），但它只对 FP8 精度生效，我们跑的是 bf16——所以不适用（这是后面要讲的"假阳性"）。

**92% 的 GPU 利用率说明 cuda graph 已经把 host 发射开销消得差不多了。** 如果利用率只有 50%，说明一半时间 GPU 在空等 CPU——那就有优化空间。92% 意味着剩下的 8% 不值得追。

### 6.4 这些 kernel 在代码里的哪里？

因为 cuda graph 开着，trace 里所有 kernel 的 Python location 都指向同一行：[`model_runner.py:3502`](../../python/sglang/srt/model_executor/model_runner.py#L3502) 的 `_forward_raw`。这是 cuda graph 的"代价"——你看不出每个 kernel 具体是哪行代码发的。要解决这个问题，需要关掉 cuda graph 再抓一份 trace（实验四）。

## 7. 实验三：关掉 cuda graph——把气泡逼出来量化

### 7.1 实验对象

同样的 batch=1 和 batch=8，但加上 `--disable-cuda-graph` 关掉 cuda graph（eager 模式），对比开关前后的时延。

### 7.2 数据

| batch | graph 开 | graph 关(eager) | 差值 = graph 省下的 |
|---|---|---|---|
| 1 | 6.08 ms (164 tok/s) | **14.27 ms (70 tok/s)** | **~8.2 ms** |
| 8 | 6.65 ms (1204 tok/s) | 17.34 ms (461 tok/s) | ~10.7 ms |

关图后，batch=1 的 GPU 利用率从 92% 暴跌到 **38%**（GPU 真忙 5.4ms / 墙上 14.27ms）。

### 7.3 怎么读

这是整个系列最直观的一张表。关掉 cuda graph 后：

```
eager(关图):  [GPU 5.4ms 在算] + [8.6ms 在空等 host 发射]  = 14.27ms/步, 利用率 38%
cuda graph:   整个 forward 录成一张图回放, 8.6ms 发射开销被一把消掉 → 6.08ms/步, 利用率 92%
```

**cuda graph 的全部价值，就是消掉这 ~8.6ms/步的 host 发射空隙。** 一次 forward 有几百个 kernel（GEMM、attention、norm、activation...），eager 模式下 CPU 要逐个发射，每个 `cudaLaunchKernel` 调用有 ~5-10μs 延迟，几百个累积就是几毫秒。cuda graph 把它们录成一张图，之后一次 `cudaGraphLaunch` 全部搞定。

**你刚刚亲手量到了 sglang 用 cuda graph 的原因。**

### 7.4 意义

这个实验告诉我们两件事：

1. **cuda graph 是 sglang 最重要的性能优化之一**，它把 GPU 利用率从 38% 拉到 92%。
2. **cuda graph 盖住的那 8.6ms host 开销，在图外仍然存在**——如果有什么代码跑在 cuda graph 外面（比如 scheduler 的 Python 逻辑），那部分开销是盖不住的。这就是为什么实验五要去抓 serving 路径。

## 8. 实验四：eager trace 的源码归因——每个 kernel 是谁发的

### 8.1 实验对象

对比 graph 开和 graph 关的两份 trace 的 kernel 表，看 "Python location" 列的差异。

原始数据在 [`.contribution-scan/analysis/triage_nograph_batch1.txt`](../../.contribution-scan/analysis/triage_nograph_batch1.txt)。

### 8.2 数据

| Kernel | graph 开时的来源 | graph 关(eager)时的来源 |
|---|---|---|
| nvjet GEMM | `model_runner.py:3502` / `cudaGraphLaunch` | **`unquant.py:153 apply` / `aten::mm`** |
| FlashAttn | 同上 | **`flash_attention_v3.py:19` / `sgl_kernel::fwd`** |
| Fused Add+RMSNorm | 同上 | **`layernorm.py:248 forward_cuda`** |
| Memset (Device) | 没出现 | **`unquant.py:153 apply` / `aten::mm`** ← 新发现 |

### 8.3 怎么读

关图后，每个 kernel 都能精确追溯到源码位置：

- **nvjet GEMM** 来自 [`unquant.py:153`](../../python/sglang/srt/layers/quantization/unquant.py#L153) 的 `F.linear(x, layer.weight, bias)`——这就是 PyTorch 的 `nn.Linear`，底层调用 cuBLAS。
- **FlashAttn** 来自 [`flash_attention_v3.py:19`](../../python/sglang/jit_kernel/flash_attention_v3.py#L19) 的 `_call_fa3_kernel`——sglang 的 FlashAttention 3 实现。
- **Fused Add+RMSNorm** 来自 [`layernorm.py:248`](../../python/sglang/srt/layers/layernorm.py#L248) 的 `forward_cuda`——已经融合成一个 kernel 了（add + RMSNorm 合并），说明这里已经被优化过。

**新发现：`Memset (Device)` 370 次，占 1%。** 这是每次 GEMM 前 cuBLAS workspace 的清零操作。Fuse 表把它和 #22392 关联起来——那个 PR 用 CUTLASS 替换 nvjet 后可以消除这些 memset。但注意：**#22392 只对 FP8 生效，我们是 bf16，所以这是假阳性。**

### 8.4 "假阳性"教训

Fuse 表把 81.5% 的 GPU 时间标成 "Confirmed" 的优化机会（PR #22392），但实际上我们跑的是 bf16 不是 FP8。工具是按 nvjet 家族名匹配的，不看 dtype。

**教训：任何自动化工具给的高置信结论，都要回看 kernel dtype / 调用链 / git blame 验证后再信。**

## 9. 实验五：真实 serving 路径——scheduler 在干什么

这是整个系列的高潮。前四个实验都在 microbench 里打转，但 microbench 不经过 scheduler。真实 serving 中，scheduler 要做很多事：接收请求、分配 KV cache、管理 batch、调度 prefill/decode、处理 sampling 结果……这些都在 cuda graph 外面，是 host 开销的真正来源。

### 9.1 实验对象

用 [`scripts/profile_serving_scheduler.sh`](../../scripts/profile_serving_scheduler.sh) 起 server + 打负载 + 抓 scheduler 进程 trace。

负载：300 个请求，并发 32，input=512/output=128。

原始数据在 [`.contribution-scan/analysis/host_side_serving.txt`](../../.contribution-scan/analysis/host_side_serving.txt) 和 [`triage_serving_scheduler.txt`](../../.contribution-scan/analysis/triage_serving_scheduler.txt)。

### 9.2 bench_serving 结果

| 指标 | 值 |
|---|---|
| 吞吐 | 16.3 req/s, 输出 1067 tok/s |
| TTFT (首 token 时延) | 中位 80ms, P99 1105ms |
| ITL (token 间时延) | 中位 **8.05ms**, 均值 **26.68ms**, **Max 3356ms** |

注意 ITL 均值（26.68ms）远大于中位（8.05ms），且 Max 高达 3356ms——说明有**尾部停顿**（可能是 Python GC 或周期性调度卡顿）。这留作后续专项调查。

### 9.3 scheduler 的 GPU 利用率

20 个 scheduler 步的窗口里：**GPU busy 1081ms / 墙上 1251ms = 86% 利用率。**

即使在真实 serving 下，GPU 利用率依然很高。因为 sglang 默认开了 **overlap scheduler**（`disable_overlap_schedule=False`）：它把 CPU 侧调度工作和 GPU 计算重叠起来——CPU 在准备下一批请求时，GPU 在算当前批。这跟 cuda graph 一样，是又一个已经做好的优化。

### 9.4 host 侧到底在干什么

torch profiler 带 CPU activities，所以能看到 scheduler 的 Python 调用树：

```
event_loop_overlap                                    1265ms
└─ get_next_batch_to_run                  x74          948ms
   └─ get_new_batch_prefill               x74          941ms
      └─ _get_new_batch_prefill_raw       x74          941ms
         └─ prepare_for_extend            x4           936ms
            └─ alloc_for_extend           x4           933ms
               └─ write_cache_indices     x4           932ms   ← 热点！
run_batch                                 x20          179ms
```

**932ms 花在 `write_cache_indices` 上（仅 4 次调用，每次 ~233ms）。** 这个函数在 [`mem_cache/common.py:64`](../../python/sglang/srt/mem_cache/common.py#L64)，负责把 KV cache 的索引信息写到 GPU。

Top host 算子也印证了这一点：

```
aten::copy_    834ms  x388     ← 主要 host 开销
aten::to       833ms  x232     ┐ 同一批拷贝/dtype 转换
aten::_to_copy 832ms  x142     ┘
```

388 次 `aten::copy_`，平均每次 2.1ms——偏大，说明是阻塞型拷贝（host→device 的数据搬运）。

### 9.5 好消息：`.item()` D2H sync 几乎不存在

```
aten::item               0.11ms  x49   ← 可忽略
aten::_local_scalar_dense 0.04ms x49   ← 可忽略
```

之前有一个已知的 perf issue（#28397）：per-step 的 `.item()` 调用会强制 GPU→CPU 同步，拖慢整个 pipeline。**在这条 serving 热路径上，这个问题已经被清理干净了。** 又一次印证"这个仓库很成熟"。

### 9.6 深挖 `write_cache_indices`：找到一个真实的反模式，但已经在途

顺着热点读了 [`mem_cache/common.py`](../../python/sglang/srt/mem_cache/common.py) 的代码，发现：

- `alloc_for_extend` 在 405-415 行用 `torch.tensor(python_list)` 建小 host 张量，再 `.to(device, non_blocking=True)`。但源张量是 pageable 内存（不是 pinned memory），所以 **`non_blocking=True` 被静默忽略、拷贝实际是阻塞的**——这是 PyTorch 的经典坑。
- 同文件 `write_cache_indices` 122-126 行对 `prefix_pointers` 却**正确地 pin 了**——前后不一致。

**然后去重（查 open PR），结论是——已经在途：**

> **PR #24734** 正在重写完全相同的路径：
> - `write_cache_indices` 的 `prefix_pointers` 改 pinned + async
> - `alloc_for_extend` paged path：用向量化干掉 per-req 切片 + `torch.cat`
> - 顺带消掉 per-step sampling info 的 CPU→GPU sync
> - `memory_pool.HybridReqToTokenPool.alloc`：`select_index` 一次性 pinned + async

**这恰恰是教科书级的结论**：
1. **GPU profiling 是对的**——我们独立从实测数据定位到的唯一 host 热点，正是一位 maintainer 正在优化的地方。
2. **去重救命**——如果不查 open PR 就动手改，必然和 #24734 冲突、白做。
3. 再次印证"仓库很成熟"：连这种中等工程量的 host 优化都已经有人在做。

## 10. 总结：三条独立路径收敛到同一个结论

整个 profiling 实战走了三条完全独立的路径：

| 路径 | 方法 | 结论 |
|---|---|---|
| **静态代码扫描** | 两个 scan agent 读代码找优化点 | 热路径已成熟，机会在 host 侧调度逻辑 |
| **前向 microbench** | `bench_one_batch` + cuda graph 开/关 + batch 扫描 | 前向路径已被 cuda graph + 算子融合优化透，82% 是硬件 GEMM 墙 |
| **serving scheduler profile** | 起真实 server + `bench_serving` + 抓 scheduler trace | host 侧唯一的显著热点（`write_cache_indices`）已有在途 PR #24734 |

**三条路径全部收敛到同一个结论：**

> SGLang 的热路径（前向 + 调度）已经被 cuda graph、overlap scheduler、算子融合、sync 消除等优化覆盖得很充分。**没有躺在地上的 1 行 quick-win perf PR。** 真要做有价值的优化，得是 `write_cache_indices` 拷贝合并、尾部 GC 停顿这类需要深挖和实测验证的中等工程量改动，或者换 FP8/MoE/spec-decode 等覆盖更少的场景重新 profile。

**这本身就是一个高质量的结论：你用 GPU 实测证否了"随便扫扫就能找到 perf PR"的乐观假设，并定位了少数几个真正值得投入的方向。**

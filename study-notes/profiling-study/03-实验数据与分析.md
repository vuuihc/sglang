# 03 · 实验数据与分析

硬件:单卡 H20(96GB)· 模型:Qwen3-8B(bf16)· input=512, output=64 · decode 阶段抓 5 步稳态。

## 实验一:cuda graph 开,batch 扫描(host→compute 转折)

数据来自 `.contribution-scan/logs/run_cudagraph_on.log`(decode 稳态中位数):

| batch | 每步时延 | 吞吐 | 每 token 时延 |
|---|---|---|---|
| 1 | 6.08 ms | 164 tok/s | 6.08 ms |
| 8 | 6.65 ms | 1204 tok/s | 0.83 ms |
| 32 | 8.91 ms | 3590 tok/s | 0.28 ms |
| 64 | 13.39 ms | 4780 tok/s | 0.21 ms |

**怎么读这张表(核心):**
- **batch 1→8:工作量 ×8,但每步时延几乎不变(6.08→6.65ms,+9%)**,吞吐 ~×8。→ 小 batch 时整步几乎全是**固定开销**,GPU 大量空闲。这是气泡区。
- **batch 8→32→64:时延开始随 batch 上涨**(6.65→8.91→13.39ms)→ 计算终于主导。H20 算力弱,这堵墙来得早(~batch 32)。

## 实验二:同一份 batch=1,看 GPU 真实利用率

分析 `triage_dense_batch1.txt`(graph 开)的 kernel 表:

- GPU 真忙的 kernel 累计 **~28 ms / 5 步 = 5.6 ms/步**;墙上 6.08 ms/步 → **GPU 利用率 ~92%,气泡仅 ~8%**。
- **82% 的 GPU 时间是 `nvjet_*` GEMM**(cuBLAS 启发式矩阵乘);FlashAttn(sm90)仅 5.5%。

> ⚠️ 这推翻了"小 batch 一定 host-bound"的直觉!原因有三(见下实验三 + 04 文档):cuda graph 已消掉 host 气泡 + H20 算力弱使 GEMM 主导 + microbench 不含 scheduler。

## 实验三:cuda graph 开 vs 关(把气泡逼出来)

数据来自 `.contribution-scan/logs/run_cudagraph_off.log`:

| batch | 每步时延 graph **开** | graph **关(eager)** | 差值 = cuda graph 省下的 host 开销 |
|---|---|---|---|
| 1 | 6.08 ms(164 tok/s) | **14.27 ms(70 tok/s)** | **~8.2 ms/步** |
| 8 | 6.65 ms(1204 tok/s) | 17.34 ms(461 tok/s) | ~10.7 ms |

**关图后的 GPU 利用率**(分析 `triage_nograph_batch1.txt`):
- GPU 真忙仍是 ~5.4 ms/步(同样那些 kernel);但墙上 14.27 ms/步
- → **GPU 利用率只有 ~38%,62% 的时间在空等 host 发射下一个 kernel**

**这就是气泡,现在量化了:**

```
eager(关图):  [GPU 5.4ms 在算] + [8.6ms 在空等 host 发射]  = 14.27ms/步,利用率 38%
cuda graph:    整个 forward 录成一张图回放,8.6ms 发射开销被一把消掉 → 6.08ms/步,利用率 92%
```

cuda graph 的全部价值,就是消掉这 ~8.6 ms/步的 host 发射空隙(几百个 kernel 逐个 launch 的延迟)。**这正是 sglang 用 cuda graph 的原因,你刚刚亲手量到了。**

## 实验四:eager trace 的源码归因(附带收获)

对比两份 trace 的 "Python location" / "CPU op" 列:

| | graph 开 | graph 关(eager) |
|---|---|---|

关图后还多出一行 `Memset (Device)`(370 次,1%),映射到 `unquant.py:153` 的 cublasLt workspace —— 每次 GEMM 前的 workspace 清零。这正是 fuse 表说 CUTLASS 替换能"remove memset bubbles"的那个 memset。

## 数据小结

| 维度 | 结论 |
|---|---|
| 小 batch 整步开销 | 固定开销主导(batch 1→8 时延几乎不变) |
| cuda graph 价值 | 消掉 ~8.6ms/步 host 发射开销,利用率 38%→92% |
| 残余瓶颈 | ~5.4ms/步 GEMM 计算(82%),H20 弱算力下的**硬件墙** |
| 已融合算子 | add+RMSNorm、QK-norm、RoPE 均为单 kernel(已优化) |
| 工具假阳性 | #22392 FP8 匹配在 bf16 上不成立 |

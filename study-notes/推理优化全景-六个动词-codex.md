# 大模型推理优化：先看瓶颈，再看技术

> 不要先背 FlashAttention、PagedAttention、量化和投机解码。先弄清楚一条请求为什么慢，再看每项技术到底省了什么。

大模型推理优化的名词很多，但目标其实只有两个：

- 让一条请求更快，也就是降低延迟；
- 让同一批硬件在单位时间内生成更多 token，也就是提高吞吐。

这两个目标经常不一致。比如增大 batch（把更多请求放在一起算）通常能提高总吞吐，却可能让某一条请求等得更久。投机解码可能降低单条请求的延迟，但在系统已经满负载时，额外的草稿计算反而会抢资源。

所以，判断一项优化有没有用，不能只问“能加速多少”，还要问：**它解决了哪个瓶颈，花掉了什么资源，在什么负载下划算？**

下面用一套尽量简单的框架，把常见技术放回它们真正解决的问题里。

---

## 一、先把 GPU 想成一家后厨

这个比喻只负责建立直觉，不代替后面的技术解释。

| 后厨里的问题 | 推理系统里的问题 | 直接影响 |
|---|---|---|
| 灶火不够，菜炒不过来 | GPU 计算能力不够 | 每一步计算时间 |
| 食材送得太慢，厨师等料 | 显存带宽不够，数据搬运慢 | 每一步搬运时间 |
| 案板和冷藏区太小 | 显存容量不够 | 模型能否装下、能同时接多少单 |
| 后一道菜必须等前一道完成 | 自回归生成必须逐 token 进行 | 至少要串行执行多少轮 |

这四个问题是一套完整的关系：

- **灶火和送菜通道**决定每一轮能跑多快；
- **案板和冷藏区**决定能摆多少食材、同时做多少单；
- **出菜顺序**决定至少要跑多少轮。

### 1. 灶火和送菜通道：为什么 Decode 时 GPU 经常“没吃饱”

GPU 执行一个算子，时间大致取决于两件事中更慢的那一件：

```text
计算时间 = 需要的计算量 ÷ 实际计算速度
搬运时间 = 需要搬的数据量 ÷ 实际显存带宽

单步时间 ≈ max（计算时间，搬运时间）
```

如果计算更慢，就叫 **compute-bound**，意思是“受计算能力限制”；如果搬数据更慢，就叫 **memory-bound**，意思是“受显存带宽限制”。Roofline（屋顶线）模型只是把这两种情况画在一张图上。

![Roofline：Prefill 和 Decode 的瓶颈不同](../infographic/inference-opt-5verbs/roofline.png)

H100 的 BF16 峰值算力约为 1000 TFLOPS，HBM 带宽约为 3.35 TB/s。两者相除，得到一个大约 **300 FLOPs/字节**的分界点：平均每搬 1 字节数据，要做约 300 次浮点运算，才有机会把计算单元充分利用起来。

但 batch=1 的 Decode 很像矩阵乘向量。模型每生成一个 token，都要读一遍大量权重，而每个权重只参与很少的计算。粗略看，它的计算强度只有约 1 FLOP/字节，离 300 很远。因此这时不是 GPU 不会算，而是权重还在路上，计算单元只能等。

Prefill 和 Decode 也因此呈现出完全不同的特点：

| 阶段 | 在做什么 | 常见瓶颈 | 优化重点 |
|---|---|---|---|
| Prefill | 一次处理整段输入，很多 token 可以并行 | 更容易受计算能力限制 | 少算、低精度计算、优化长序列注意力 |
| Decode | 每轮通常只为每条请求生成一个 token | 更容易受显存带宽限制 | 少搬、合批、减少调度空隙 |

batch 为什么重要？因为把 N 条 Decode 请求放在一起算，模型权重仍然只需读一遍，却能同时服务 N 个 token。等于一次送来的食材做了 N 份菜，搬运成本被摊薄了。

### 2. 案板和冷藏区：显存容量不直接等于速度

推理时，显存主要放两类东西：

- **模型权重**：模型加载后基本固定；
- **KV Cache**：保存历史 token 在注意力层中的中间状态，随并发数和上下文长度增长。

以 Qwen3-32B 为例。它有 64 层、8 个 KV 头，每个头 128 维。若 KV 使用 BF16，每个 token 的 KV 大约是：

```text
2（K 和 V）× 64 层 × 8 个 KV 头 × 128 维 × 2 字节
= 262,144 字节
≈ 256 KB/token
```

一条 128K 上下文的请求，理论上就需要约 32 GB KV。实际部署还会受到分页、对齐、运行时缓冲区等因素影响。

显存变大不会自动缩短一次矩阵乘，但它能通过两条路转化成性能：

1. 能放下更多并发请求，batch 可以更大，吞吐更高；
2. 能保留更多历史前缀，缓存命中率更高，重复的 Prefill 可以直接跳过。

所以显存容量更像后厨的案板和冷藏区：它不负责炒菜，但空间太小，厨师就无法同时处理更多订单。

### 3. 出菜顺序：自回归带来的串行依赖

常规大模型生成第 N 个 token 时，必须先知道第 N-1 个 token。要生成 100 个 token，通常就要顺序执行 100 轮。

前面的计算优化和搬运优化，只能缩短每一轮的时间；它们不能自动把 100 轮变成 50 轮。只有投机解码、多 token 预测这类技术，才会直接尝试缩短这条关键路径。

把三件事放在一起，可以得到全文最重要的一组关系：

```text
总时间 ≈ 串行轮数 × 每轮时间

每轮时间 ≈ max（计算量 ÷ 实际计算速度，搬运量 ÷ 实际显存带宽）

同时还要满足：模型权重 + KV Cache + 运行时缓冲区 ≤ 可用显存
```

后面的技术看起来五花八门，其实都是在改这几项。

## 二、六个动作：不算、少算、少搬、少占、打满、少走几轮

这六个动作不是严格的学术分类，也不是互斥的。一个好技术经常同时命中两三项。它们的作用是帮助我们快速看懂一项技术的主要收益。

### 动作一：不算——复用已经得到的结果

最便宜的计算，是不再重复计算。

#### KV Cache：同一条请求内复用

没有 KV Cache，生成第 t 个 token 时，前面 t-1 个 token 的 K 和 V 都要重新计算。生成 n 个 token，总工作量会从 1 一直累加到 n。保存 K/V 后，每轮只需为最新 token 计算一次新的 K 和 V。

注意力打分本身仍然要读取历史 KV，序列越长，单轮读取量越大。所以 KV Cache 没有让历史消失，而是把“反复重算历史”变成了“保存并读取历史”。这是一笔非常划算、但绝非免费的交易：**用显存容量和显存带宽，换掉数量大得多的重复计算。** 后面几乎所有 KV 优化，都在处理这笔交易带来的新问题。

#### Radix Cache / Prefix Cache：在不同请求之间复用

很多请求有相同的开头，例如系统提示词、固定的 few-shot 示例和多轮对话历史。SGLang 用 Radix Cache 索引这些公共前缀。新请求命中后，可以直接复用已经算好的 KV，跳过对应的 Prefill。KV Cache 解决一条请求内部的复用，Prefix Cache 则把复用范围扩大到了不同请求之间。

#### HiCache：把缓存池扩到 CPU 内存和存储

GPU 显存有限，放不下的冷数据可以下沉到 CPU 内存甚至 SSD。命中时再把 KV 搬回 GPU。这样表面上增加了搬运，为什么仍然归到“不算”？因为比较对象不是“搬或者不搬”，而是“搬回 KV”与“重新执行整段 Prefill”。

继续用 Qwen3-32B 粗算：4K token 的 BF16 KV 约 1 GB，而重新执行 4K token 的 Prefill 需要大约 `2 × 32B × 4096` 次浮点运算。只要 load-back 没有被大量小块传输、PCIe 争用或存储抖动拖垮，搬回 1 GB KV 通常比重算整段 Prompt 便宜得多。HiCache 的关键指标因此不是“有没有命中”一个数，而是命中在哪一层、搬回用了多久、最终省下多少重算。

后厨里，这相当于高汤熬好后先保存。灶边放不下，就放冷藏库；下次取回来，仍然比从头熬一锅快。

### 动作二：少算——减少真正需要执行的计算

少算主要在 Prefill、大 batch 或其他计算单元比较繁忙的场景中见效。如果系统本来就在等数据，继续减少 FLOPs 未必能明显加速。这也是为什么不能把所有量化都笼统地说成“降低计算量”。

- **FP8 / W8A8 计算量化**：权重和激活都用低精度参与矩阵乘，能直接使用吞吐更高的低精度 Tensor Core。它同时会少搬、少占，但在 Prefill 或大 batch 下，主要收益确实是“同样时间能做更多计算”。
- **稀疏注意力**：不再让每个 token 查看全部历史位置，只选择局部窗口或一部分重要 token。它省的不只是注意力打分，还包括对应 KV 的读取。GLM-5.2 的 IndexShare 更进一步：多层稀疏注意力共用索引结果，避免每层重复做一遍“该看哪些 token”的筛选。
- **MoE**：模型有很多专家，但每个 token 只激活其中少数几个。Qwen3-30B-A3B 总参数约 30B，每个 token 实际激活约 3B；DeepSeek-V3 则是 671B 总参数、37B 激活参数。模型容量可以很大，每个 token 的计算量却不必等比例增长。

MoE 很能说明一个常见误区：**计算少，不等于部署简单。** 所有专家权重仍要存放；专家分布在多卡时，token 还要跨卡发送；路由不均匀时，热门专家所在的卡会成为短板。它省下的计算，可能又以容量、通信和负载均衡问题的形式回来。

### 动作三：少搬——减少每轮从显存读取和写回的数据

这是 Decode 的主战场。

#### 少搬权重：Weight-only 量化

AWQ、GPTQ 等方法把权重压到 4 bit 或更低，计算前再解量化。解量化会增加计算，但权重读取量大幅下降，所以在受带宽限制的 Decode 阶段仍可能明显加速。

这件事听起来反直觉，却很重要：**有时多算一点，反而能更快，因为真正的瓶颈是搬数据。** 这也划清了两类量化的主账：W8A8 / FP8 更偏向低精度计算，Weight-only 量化更偏向压缩权重搬运。它们都叫量化，适用条件并不相同。

#### 少搬 KV：KV 量化和更小的 KV 结构

- KV 量化把 BF16 KV 压成 FP8、INT8 或更低精度；
- GQA 让多组 Query 头共享更少的 KV 头。前面的 Qwen3-32B 算例中，64 个 Query 头只对应 8 个 KV 头；
- MLA 把各个头的 KV 压缩成更小的 latent。DeepSeek-V3 使用 MLA，主要收益之一就是减少长上下文下的 KV 体积和每轮读取量。

#### 少搬中间结果：FlashAttention 和算子融合

朴素注意力会产生很大的中间矩阵，并把它写入显存后再读回来。FlashAttention 通过分块和 online softmax，让很多中间结果留在片上 SRAM，不必反复落到 HBM。数学结果没有变，数据走的路变短了。它对 Prefill 和长序列尤其重要，因为这时中间矩阵才足够大。

`torch.compile`、TensorRT 等编译和融合方案也在做类似的事：原来多个小算子各读写一次显存，现在合成一个大算子，中间结果尽量不离开芯片。这里的 kernel，指的就是在 GPU 上执行的一段计算程序。

后厨里，这相当于一次把需要的食材拿齐，在灶台边连续完成几道工序，不要每切一刀都把半成品送回仓库。

### 动作四：少占——减少显存浪费和状态体积

少占不一定直接减少单步延迟，它的收益通常通过两条路兑现：一是同样显存放下更多并发，把 batch 开大；二是留下更大的前缀缓存池，提高“不算”的命中率。容量是条件，不是时间本身。

#### PagedAttention：按需分配 KV 空间

如果按请求的最大可能长度预留一整块连续显存，短请求会留下大量空洞；请求不断进出，还会产生难以利用的碎片。PagedAttention 借用操作系统分页的思路，把 KV 切成固定大小的块，需要多少就分多少，逻辑上连续的 KV 不必在物理显存中连续。

它不改变注意力的数学计算，也不会凭空减少这条请求必须读取的 KV；它解决的是显存分配和碎片浪费。

#### GQA、MLA 和 KV 量化：状态本身更小

这些技术同时属于“少搬”和“少占”。KV 变小后，每轮读取量下降，同样的显存也能容纳更多请求。模型结构上的一次改动，会同时影响 kernel、缓存布局和调度器能接受的最大 batch，这就是为什么它们不能只放进一个格子。

#### KV 驱逐和分层卸载：把不常用的状态移出去

滑动窗口可以丢掉较远的 KV，代价是模型看不到完整历史；HiCache 则把较冷的 KV 放到 CPU 内存或存储中，代价是命中时需要搬回来。

### 动作五：打满——减少硬件等待和系统空隙

“打满”不是指某个监控数字必须达到 100%，而是减少各类空转：batch 里有空位、Prefill 和 Decode 互相堵塞、GPU 等 CPU 发任务、多卡互相等待，背后是不同问题，不能靠同一个开关解决。

- **请求之间有空位 → Continuous Batching**：请求完成后立刻移出 batch，新请求随时补进来，不必等整批请求一起结束。它提高的是吞吐，但请求持续插队和合批也会影响单请求延迟的稳定性。
- **Prefill 和 Decode 互相干扰 → Chunked Prefill / PD 分离**：单机上可以把长 Prompt 切成小块，与 Decode 穿插执行；集群上可以把两个阶段放到不同实例，各自选择合适的 batch 和硬件。前者要调好分块大小，后者要承担 KV 传输。
- **单卡一轮算得太慢 → TP / PP / EP**：TP 拆一层里的矩阵，PP 拆不同层，EP 拆 MoE 专家，让多张卡同时参与执行。这里真正与“打满”相关的，不是“单卡装不下”，而是如何让各卡都有有效工作：TP 要隐藏集合通信，PP 要减少流水线空泡，EP 要做好专家负载均衡。并行度开得越大，通信和同步成本也越高。
- **GPU 等 CPU 发任务 → CUDA Graph**：把一轮固定的 GPU 操作提前录制，之后整图回放，减少上百个小 kernel 的启动开销。代价是输入形状不能随意变化，通常要为不同 batch size 预录多张图。
- **GPU 等下一轮调度 → Overlap Scheduler**：GPU 执行当前 batch 时，CPU 同时处理上一轮结果并准备下一批数据，把 Python 调度时间藏到 GPU 执行时间里。
- **多卡等通信 → 通信与计算重叠**：一部分数据传输时，同时执行不依赖它的计算。它不减少通信量，但可以把一部分通信时间藏起来。

后厨里，Continuous Batching 是“空出一个灶眼就马上补单”；Overlap Scheduler 是“炒当前这道菜时，下一道菜已经切好”；CUDA Graph 是“固定菜不用每次重新口头交代整套步骤”。

### 动作六：少走几轮——缩短串行生成路径

“破串行”容易让人误以为完全取消了逐 token 依赖。更准确的说法是：**用额外工作换取一次确认多个 token，从而减少大模型串行执行的轮数。**

#### 投机解码

先用一个更便宜的草稿模型猜出后面几个 token，再由目标模型一次并行验证。猜对几个，就可以一次接受几个。只要验证方法正确，最终采样分布仍可与目标模型逐 token 生成保持一致。这里真正决定收益的是接受率和平均接受长度：草稿一次猜得再多，如果大部分在第一个 token 就被拒绝，也没有意义。

它之所以可能加速，还是因为小 batch Decode 常受显存带宽限制。目标模型验证多个候选 token 时，权重不必按 token 数等比例重复搬运，可以利用原本闲置的计算能力。Batching 是拿这些闲置算力服务更多请求，投机解码则是拿它验证同一条请求的多个未来 token。

但它不是免费午餐：

- 草稿模型或额外预测头要占显存、花计算；
- 草稿猜得不准时，很多验证会浪费；
- 高负载、大 batch 时，原本闲置的计算能力已经被其他请求用掉，收益可能明显下降。

#### MTP：模型训练时就准备好多 token 预测能力

MTP 是 Multi-Token Prediction，即“多 token 预测”。DeepSeek-V3 和 GLM-5.2 都把这类能力放进了模型结构或训练目标中，可用于投机解码。GLM-5.2 还专门提高了 MTP 的平均接受长度。

后厨里，这不是盲目提前做菜，而是先根据历史订单准备几道大概率会点的菜，再由正式订单确认。闲时可能省时间，满负载时则未必值得占用厨师。

## 三、全景图：六个动作发生在哪四层

“不算、少算、少搬、少占、打满、少走几轮”回答的是：**这项技术在省什么。**

还缺另一条轴：**它在系统的哪一层发生。**

大模型推理系统从外到内，可以分成四层：

```text
请求与流量
   │
   ▼
┌─────────────────────────────────────────────┐
│ ④ 服务与集群层：请求怎么排，卡和实例怎么协作       │
│    batching / chunked prefill / PD / TP·PP·EP │
├─────────────────────────────────────────────┤
│ ③ 缓存与运行时层：哪些状态复用，KV 放在哪里         │
│    KV Cache / Radix Cache / PagedAttention   │
├─────────────────────────────────────────────┤
│ ② 算子执行层：一次 forward 具体怎么算、怎么搬       │
│    量化 / FlashAttention / fusion / CUDA Graph│
├─────────────────────────────────────────────┤
│ ① 模型结构层：模型天生要算多少、产生多少状态         │
│    GQA·MLA / MoE / 稀疏注意力 / MTP             │
└─────────────────────────────────────────────┘
   │
   ▼
GPU 计算、显存与互联
```

这四层有明确的依赖关系：模型结构决定每个 token 天生需要多少计算和 KV；算子层决定这些计算怎样在具体硬件上执行；缓存层管理执行过程中产生的状态；服务层再把许多请求、许多卡和许多实例组织起来。

因此，全景图不应该是一张平铺的技术名单，而应该是“**四层架构 × 六个动作**”。下面按层看。

### 3.1 模型结构层：出厂时已经决定的推理成本

这一层由模型训练方决定。推理框架不能把普通 MHA 模型临时改成 MLA，也不能给没有 MTP 头的模型凭空加上同等能力；它能做的是提供相匹配的 kernel、缓存布局和调度方式，把结构收益兑现出来。

| 技术 | 主要动作 | 改变了什么 | 收益与代价 |
|---|---|---|---|
| GQA / MLA | 少搬、少占 | 每个 token 产生的 KV 更小 | 长上下文和大并发更省；需要专用 KV 布局与 Attention kernel |
| MoE | 少算 | 每个 token 只激活少数专家 | 激活计算下降；全部专家仍占容量，跨卡路由复杂 |
| 稀疏注意力 / DSA | 少算、少搬 | 每个 token 只查看部分历史 | 长上下文收益大；索引本身也有计算和存储成本 |
| MTP | 少走几轮 | 一次预测多个未来 token | 可用于投机解码；增加训练、显存与验证成本 |

DeepSeek-V3 的 MLA、MoE、MTP 正好覆盖了三个不同方向；GLM-5.2 的稀疏注意力、IndexShare 和改进 MTP，则更明显地围绕 1M 上下文的计算量和生成延迟做文章。这些不是孤立的论文点子，而是一组在模型结构层预先做好的推理取舍。

### 3.2 算子执行层：同一张计算图，怎么在 GPU 上跑

这一层最接近硬件。重点不是改模型语义，而是让同样的前向计算少算、少搬、少等。

| 技术 | 主要动作 | 改变了什么 | 收益与代价 |
|---|---|---|---|
| FP8 / W8A8 | 少算、少搬 | 低精度矩阵乘 | Prefill、大 batch 收益明显；有精度与硬件支持边界 |
| AWQ / GPTQ | 少搬、少占 | 压缩权重，运行时解量化 | Decode 少读权重；多出解量化计算 |
| FlashAttention / FlashInfer | 少搬 | 中间结果尽量留在片上存储 | 长序列收益大；不同硬件和 KV 结构需要不同后端 |
| 算子融合 / `torch.compile` | 少搬、打满 | 合并小算子，减少中间读写和启动次数 | 形状动态、图断裂时收益受限 |
| CUDA Graph | 打满 | 整图回放，减少 CPU 启动开销 | 小 batch Decode 更敏感；需要管理多种固定形状 |

这里也能看出 Prefill 和 Decode 的区别：Prefill 更关心低精度算力能否真正跑起来，Decode 更关心每轮少读多少权重和 KV。一个 kernel 在某个阶段很快，不代表另一个阶段也同样受益。

### 3.3 缓存与运行时层：保存什么、复用什么、放在哪里

这一层管理的不是模型参数，而是请求执行过程中不断增长和变化的状态。KV Cache 是地基，前缀复用、分页分配和分层存储都建立在它之上。

| 技术 | 主要动作 | 改变了什么 | 收益与代价 |
|---|---|---|---|
| KV Cache | 不算 | 保存同一请求的历史 K/V | 免掉历史重算；消耗容量和带宽 |
| Radix / Prefix Cache | 不算 | 在不同请求间复用公共前缀 | 跳过重复 Prefill；效果取决于命中率和缓存策略 |
| PagedAttention | 少占 | KV 按块分配而非整段预留 | 减少碎片、提高并发；不减少必要的计算和读取 |
| KV 量化 | 少搬、少占 | 用更低精度保存 KV | 长上下文收益直接；有精度和 kernel 适配成本 |
| HiCache | 不算、少占 | KV 在 GPU、CPU、存储间分层 | 扩大缓存池；命中时要支付 load-back 延迟 |
| KV 驱逐 / 滑动窗口 | 少占、少搬 | 丢弃或不再读取较远 KV | 容量和带宽下降；可能损失长程信息 |

这一层最容易出现“指标看起来变好，端到端反而变差”的情况。比如 HiCache 命中率提高了，但 load-back 太慢；KV 量化把缓存减半了，但解码 kernel 不成熟；PagedAttention 放进了更多请求，但调度策略没有把容量转化成有效 batch。状态管理必须和执行、调度一起看。

### 3.4 服务与集群层：把请求、实例和多张卡组织起来

这一层决定谁先算、和谁一起算、在哪张卡上算。它主要减少各种空转，也负责在延迟、吞吐和服务稳定性之间取舍。

| 技术 | 主要动作 | 改变了什么 | 收益与代价 |
|---|---|---|---|
| Continuous Batching | 打满 | 请求按 token 步动态进出 batch | batch 更饱满；调度和延迟控制更复杂 |
| Chunked Prefill | 打满 | 长 Prompt 切块后与 Decode 穿插 | 减少 Decode 抖动；块太小会损失 Prefill 效率 |
| PD 分离 | 打满 | Prefill、Decode 放在不同实例 | 两边独立扩缩容；需要传 KV |
| TP / PP / EP | 打满、扩展 | 矩阵、层或专家分到多卡 | 多卡共同工作；引入通信、空泡和负载不均 |
| Overlap Scheduler | 打满 | CPU 调度与 GPU 执行重叠 | 减少步间空档；异步状态管理更复杂 |
| 投机解码调度 | 少走几轮、打满 | 草稿生成与目标验证协同 | 小 batch 延迟可能明显下降；高负载时会抢算力 |

把 TP / PP / EP 放在这里，重点不是“模型终于装下了”，而是多卡执行怎样影响系统利用率。TP 的关键是集合通信能否被隐藏，PP 的关键是流水线有没有空泡，EP 的关键是专家负载是否均匀。单卡装不下只是采用并行的一个原因，不是“打满”的逻辑本身。

## 四、把四层架构落到 SGLang

源码路径适合开发者查实现，但对只想建立全局认识的读者，先看请求和状态怎样流动更有用。

<!-- 配图位置：SGLang 四层请求链路架构图。正式图片确认后替换此注释。 -->

```text
客户端 / OpenAI 兼容 API
          │
          ▼
Tokenizer Manager ───────────────────────────────┐
文本转 token、请求预处理                           │ 流式返回
          │                                      │
          ▼                                      │
Scheduler                                        │
请求准入、前缀匹配、Continuous Batching、分块 Prefill │
          │                                      │
          ├── Cache Controller / KV Pool          │
          │   Radix Cache、分页分配、HiCache       │
          │                                      │
          ▼                                      │
Model Worker / Model Runner                       │
Attention 后端、量化、MoE、CUDA Graph、投机验证      │
          │                                      │
          ▼                                      │
Detokenizer Manager ──────────────────────────────┘
token 转文本
```

这条链路和前面的四层可以直接对上：

- 模型结构层由加载的 Qwen、DeepSeek、GLM 等模型决定；
- 算子执行层集中在 Model Runner 和各种 Attention、MoE、量化后端；
- 缓存与运行时层围绕 Radix Cache、KV Pool、PagedAttention、HiCache 展开；
- 服务与集群层由 Scheduler、Router、并行 Worker 和 PD 实例共同完成。

多卡场景下，TP / PP / EP 位于 Model Worker 内部及其通信组中；PD 分离则改变整条请求路径：请求先到 Prefill 实例，KV 传输后再由 Decode 实例继续生成。投机解码同时跨越模型结构、算子执行和调度三层，也因此比“换一个快 kernel”更难做稳。

这张架构图的价值，不是告诉读者某个类在哪个文件，而是让人看出：一项优化改动后，会影响哪些上游和下游。例如 MLA 不只需要一个 Attention kernel，还会改变 KV Pool 的布局和 Scheduler 能承载的 batch；HiCache 不只是一套存储，还会反过来影响请求准入和 Prefill 是否值得跳过。

## 五、看一项新技术，只问四个问题

以后看到新的推理优化名词，可以按这个顺序判断：

1. **当前到底慢在哪里？** 是计算、显存带宽、显存容量、CPU 调度、卡间通信，还是逐 token 串行？
2. **它减少了什么？** 不算、少算、少搬、少占、少等，还是少走几轮？
3. **它额外花了什么？** 精度、显存、计算、通信、灵活性，还是工程复杂度？
4. **它服务哪个目标？** 单条请求延迟、总吞吐、最大上下文、最大并发，还是“先让模型跑得起来”？

第四问很重要。比如：

- PagedAttention 主要提高显存利用率和可承载并发，不代表单条请求一定更快；
- TP 可以解决单卡装不下，也可能降低单条请求延迟，但通信很重时可能适得其反；
- 投机解码常对小 batch 延迟更友好，对已经满载的吞吐场景未必有利；
- GLM-5.2 的稀疏注意力和 IndexShare 主要面向超长上下文成本，短上下文不一定能获得同样收益。

回答完这四个问题，一项技术的价值边界通常就清楚了。

## 结语

大模型推理优化不是一张需要背下来的名词表，而是一组资源交换：

- 用显存换重复计算，这是 KV Cache；
- 用少量解量化计算换更少的权重搬运，这是 Weight-only 量化；
- 用更复杂的内存管理换更高的显存利用率，这是 PagedAttention；
- 用卡间传输换 Prefill 和 Decode 各自更稳定的资源使用，这是 PD 分离；
- 用草稿计算和额外显存换更少的目标模型串行轮数，这是投机解码。

技术会不断更新，国内模型也已经给出了很好的现实例子：Qwen3 用 GQA 和 MoE 控制 KV 与激活计算，DeepSeek-V3 用 MLA、MoE 和 MTP 同时处理搬运、计算和串行轮数，GLM-5.2 又把稀疏注意力、IndexShare 和改进的 MTP 推到 1M 上下文场景。

真正稳定的方法不是记住今天有哪些技术，而是先找到瓶颈，再算清交易。只要这两步没错，新名词通常都能放回熟悉的位置。

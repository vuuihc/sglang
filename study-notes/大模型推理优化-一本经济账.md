## 读之前先立坐标系

推理优化可以粗粗收成六个动词——**不算、少算、少搬、少占、打满、破串行**。它们省的不是同一种东西：

| 动词 | 在省什么 |
|---|---|
| 不算 | 整段已经算过的工作（命中缓存就跳过） |
| 少算 | 计算量 / 用更便宜的精度算 |
| 少搬 | 每轮从 HBM 读的字节 |
| 少占 | 显存容量，换更大 batch 或更长上下文 |
| 打满 | GPU 空转（调度空隙、launch 间隙） |
| 破串行 | 自回归必须一轮一个 token 的轮数 |

全文只反复出现两个阶段名：**Prefill** 是一次并行读完输入、吐出第一个 token 之前；**Decode** 是之后一个一个往外蹦 token。前者常撞**算力墙**，后者常撞**带宽墙**——阶段一变，最优动词就变。这是所有「价签换脸」的地基。

---

先讲一件对不上的事。EAGLE3 这类投机解码，论文里报到 6.5× 加速；我们把它原样搬到一张 H20 上，并发 32 时只拿到 0.29×——不是快了，是慢了三倍多。没有人作假：论文测的是 batch=1 的世界，我们测的是打满并发的世界，同一项技术在两个世界里价签完全不同。

优化技术的介绍通常从最好看的那个加速比开始。但真正要算清收益时，问题是另一组：这个数字在哪种负载下成立？并发变高后还成立吗？省下的是算力、带宽、容量，还是串行轮数？论文里的「×N」，和你线上看到的「+几个点」，为什么经常对不上？

这篇就把这些数字逐个量清：论文给的是某个理想负载下的漂亮数字，我们做的是实测——在同一张 H20、同一套 SGLang 上，把每项优化逐个开关，量出它在真实批量下到底值多少收益。

有一条边界先说死：下面每张对比表都是**同一套框架里的单开关消融**（技术开 vs 关、或低精度 vs 原精度），不是跨框架评测。所以像 Radix Cache 的 +153%，量的是「有没有这项优化」，不是「SGLang 的实现比别家强多少」——后者要另做 SGLang vs vLLM 那类横评，我们这次没跑。

下文每个动词按同一张骨架展开：**它到底在省什么** → **论文的数据和我们的实测怎么对账** → **哪里违反常识、为什么** → **落到工作里该怎么用**。需要画图的地方只画两类：对比曲线，以及讲不清就画出来的原理示意。先给一张总表，方便跳读：

| 动词 | 技术或开关 | 最醒目的实测价签 |
|---|---|---|
| 不算 | Radix Cache | 共享前缀负载下，开启后吞吐 **+153%**（2.53×），中位 TTFT 降到 **1/8.82** |
| 少算 | FP8 | Prefill 相吞吐 **+46.0%**；Decode 相只有 **+6.1%** |
| 少搬 | AWQ 4bit | 单请求吞吐 **+31.7%**；并发 32 时反而 **-19.3%** |
| 少搬 | FA3 vs torch_native | 4K/8K Prefill 吞吐分别 **+39.9%/+23.1%** |
| 少占 | FP8 KV Cache | 相同显存池从 474,376 增至 948,752 token，恰好 **2×** |
| 少占 | MLA（DeepSeek-V2-Lite 对照） | 同卡同 mem-fraction 下 KV 池约 **3.71×** Qwen3-8B GQA；4K→30K Mean ITL 仅 **+21.5%** |
| 打满 | Overlap Scheduler | 并发 8 和 32 的吞吐都约 **+10.5%** |
| 打满 | CUDA Graph | 开图后 bs=1 每步 14.27→6.08ms，快 **2.35×** |
| 破串行 | EAGLE3 | 并发 1 为 **1.87×**；并发 4 已降到 **0.92×**，之后继续转负 |

**这张表最该记的不是哪一行数字最大，而是价签会换脸。** 同一项优化换个负载就换个价：FP8 在 Prefill 很值钱，到 Decode 只剩个位数收益；AWQ 和投机解码在低并发赚钱，高并发却会反噬。优化没有脱离工作负载的统一价格——所以下面每一节，我们都把「什么条件下这个价签成立」写在数字旁边。表中 CUDA Graph 一行来自**同系列既有实验**（旁证），其余主结果均在本节口径下单卡消融。

## 一、不算：共享前缀命中后，整段 Prefill 消失

### 1. 技术原理

Radix / Prefix Cache 的核心不是「把 Prefill 算快一点」，而是**让重复前缀不再进 GPU**。

同一条请求内部，KV Cache 已经把「重算历史」换成了「保存并读取历史」。跨请求时，系统提示、few-shot、多轮历史往往高度重合。SGLang 用一棵基数树（radix tree）按 token 前缀索引已经算好的 KV：新请求进来先走树，命中多长就跳过多长 Prefill，只补算分叉之后的尾巴。

这和 CPU 上的 memoization 是同一类交易：**用显存容量换免算**。命中的是整段已经做过的矩阵乘，不是某个 kernel 的微调。

![Radix Cache 原理：公共前缀命中后跳过 Prefill](assets/fig-radix-principle.png)

### 2. 论文的数据 vs 我们的实测

框架论文和博客里，共享系统提示 / 多轮对话场景下，前缀缓存常常把 TTFT 压到原来的几分之一，总吞吐成倍上涨——因为省掉的是整段 Prefill，不是几个百分点的 kernel 优化。这些数字通常建立在**高前缀重叠、缓存池够大、命中路径稳定**的假设上。

我们构造 32 组共享前缀，每组 8 条请求（共 256 条），公共系统提示约 2K token，再给每条请求接不同问题。下表吞吐是整个负载的聚合值、TTFT 是 256 条的中位数——是接近真实批量场景的整体口径，不是单请求的孤立加速：

| Radix Cache | 输出吞吐 | 中位 TTFT | 中位 ITL |
|---|---:|---:|---:|
| 开（命中跨请求前缀，跳过重复 Prefill） | 996.98 tok/s | 288.00 ms | 9.68 ms |
| 关（每条请求都从头 Prefill） | 393.98 tok/s | 2540.44 ms | 9.68 ms |

开启的收益：吞吐从 393.98 涨到 996.98 tok/s（+153%，2.53×），中位 TTFT 从 2540 压到 288ms（降到 1/8.82）。量级和「共享前缀场景前缀缓存极值钱」的叙事一致；我们没有复现某个具体论文的 ×N，因为负载构造不同，但对账方向是同一笔账。

**这个 +153% 比的是什么，得说死。** 它是「有跨请求前缀复用 vs 完全不复用」的差，不是「SGLang 的基数树比朴素前缀缓存强多少」。后者是另一个问题——树结构做的是**最长前缀匹配 + 按前缀树淘汰**，朴素实现往往只能整段 prompt 精确命中、命中率和内存效率都更差；但要量出这份实现差值多少，得另做一组 SGLang vs vLLM / 朴素 prefix cache 的跨框架横评，本文这套单开关消融没覆盖。所以这一行请当「前缀复用这件事值多少」来读，别当「SGLang 实现红利」来读。

### 3. 异常与反常识

**Decode 完全没变快。** 中位 ITL 开/关都是 9.68ms。很多人第一次看到会愣一下：缓存不是优化吗，为什么生成速度不动？

这里要分清两层缓存：**单请求内的 KV Cache** 和**跨请求的 Prefix Cache** 是两回事。decode 每步读的是自己请求那段（增长中的）KV，它一直由单请求 KV Cache 提供，和 prefix cache 开不开无关——不管前缀是命中缓存搬进来的、还是刚现算出来的，进入 decode 后两组面对的 KV 池内容完全一样，每步读的字节数也一样，ITL 自然一致。所以 prefix cache 是**纯 prefill 阶段、跨请求**的优化：命中省的是**到达第一个 token 之前**的工作，进入 Decode 稳态后每轮仍要搬权重、读 KV，它帮不上忙。这把「不算」和「少算 / 少搬」的边界画得很清楚：免掉的是整段 Prefill，不是每步 Decode。

另一个容易误判的点：命中率若很低，账单会迅速缩水。缓存池太小、前缀各不相同、或命中落在 CPU/SSD 层却搬不回来，都会把「免算」变回「又算又搬」。

### 4. 实践启示

- 先问产品形态有没有稳定公共前缀：RAG 系统提示、Agent 工具说明、多轮客服历史。有，再谈 Radix / 分层缓存；没有，这项优化接近空转。
- 监控不要只看「命中率」一个数：还要看命中前缀长度、命中在哪一层、搬回耗时。命中在 SSD 却要重算更划算时，策略就要改。
- 评测必须构造真实重叠；用完全随机 prompt 测前缀缓存，等于给它零分卷。

> 💰 **一句话价签**：有稳定公共前缀，命中就免掉整段 Prefill——TTFT 砍到零头（我们 1/8.82），但 Decode 一分不降。没有重叠前缀，这项优化接近白开。

## 二、少算：FP8 只在算力墙下值大钱

### 1. 技术原理

FP8 / W8A8 把权重和激活都压到更低精度，让矩阵乘跑在吞吐更高的低精度 Tensor Core 上。它顺带也少搬、少占，但在 Prefill 和大 batch 下，主收益是：**同样时间做更多乘加**。

适用条件很硬：**只有算力是瓶颈时，省计算才省时间**。系统本来就在等显存带宽，砍掉的是闲着的算力，墙上的钟几乎不动。

![先找墙再选动词：算力墙 vs 带宽墙](assets/fig-two-walls.png)

### 2. 论文的数据 vs 我们的实测

硬件与框架材料里，FP8 在算力密集的 GEMM 上常被报出接近硬件峰值的显著加速（量级常见是「明显快一截」，具体倍数随卡、形状、是否融合 kernel 变化很大）。那些数字多半对应**大矩阵、高占用、算力墙**设定，而不是「任意 Decode 服务默认 +50%」。

我们分别测两种负载：长输入短输出的 Prefill 相，以及短输入长输出的 Decode 相。路径上走的是 serving 框架的 **FP8 权重量化 / 低精度 GEMM 路径**（相对 BF16 基线只换精度相关配置，不改负载与调度）；这里验收的是**吞吐账单**，不是答案逐 token 对齐——精度与校准是另一本账：

| 负载 | BF16 | FP8 | FP8 收益 |
|---|---:|---:|---:|
| Prefill 相输出吞吐 | 8.34 tok/s | 12.18 tok/s | **+46.0%** |
| Prefill 相中位 TTFT | 3975.44 ms | 2740.74 ms | **-31.1%** |
| Decode 相输出吞吐 | 3695.08 tok/s | 3919.27 tok/s | **+6.1%** |
| Decode 相 Mean ITL | 8.04 ms | 7.67 ms | **-4.6%** |

![FP8 在 Prefill 与 Decode 的吞吐收益对比](assets/fig-fp8-prefill-vs-decode.png)

同一份 FP8，Prefill 接近一半吞吐增益，Decode 只剩 6.1%。和「算力墙值钱、带宽墙缩水」的原理对齐；也解释了为什么不能拿训练侧或纯 Prefill 海报数字，直接当线上 Decode SLA 的承诺。

### 3. 异常与反常识

**同一种量化，两个阶段完全两个价。** 这不是 FP8「有时灵有时不灵」，而是瓶颈换了：Prefill 更接近算力墙，低精度计算单元能直接兑现；Decode 主要在搬权重，砍计算只省掉一部分本来就没占满的算力。

另一个隐蔽点：FP8 路径依赖 kernel 与数值路径是否真的走到低精度单元。名义上开了 FP8，若大量算子仍回退 BF16，或缩放因子处理拖后腿，实测会远低于纸面。

### 4. 实践启示

- 问「FP8 快多少」之前，先写清阶段：Prefill / Decode、batch 多大、序列多长。
- Prefill 重、长文档、高并发 prefill 的集群，优先评估计算量化；纯低并发聊天 Decode，预期要收着。
- 精度与校准是另一本账：吞吐账单和「答案变没变」要分开验收。

> 💰 **一句话价签**：只在算力墙下值大钱。Prefill +46%，Decode 只剩 +6%。买之前先问一句：你现在撞的是哪面墙。

## 三、少搬：让每一轮从显存少读一些字节

少搬是 Decode 的主战场。每轮搬两样东西：**权重**，以及这批请求的 **KV**。路径不同——权重量化、注意力融合 kernel、KV 结构压缩——但账本同一句：带宽墙下，少读比多算更值钱。

### A. AWQ 4bit：多算一点，反而更快

#### 1. 技术原理

AWQ 等 weight-only 量化只把权重压到 4bit，计算前再解压回高精度。解压是**额外计算**——比 BF16 还多做了一步。它在 Decode 下仍可能更快，因为瓶颈是**搬权重**：4bit 读入再解压，往往仍比反复从 HBM 拖 BF16 权重便宜。

这和 FP8 的 W8A8 不是同一笔交易：后者主打少算，前者主打少搬。

#### 2. 论文的数据 vs 我们的实测

AWQ 论文配套 TinyChat，在桌面/移动 GPU 上相对 HuggingFace FP16 报过 **3× 以上** 的生成加速。那是边缘部署、小 batch、对 HF 朴素路径的对比，不是和生产级 serving（连续批处理、CUDA Graph、融合 kernel）的同台竞技。

我们在 H20 + SGLang 上只改模型精度路径（BF16 权重 → AWQ 4bit 权重）：

| 并发 | BF16 吞吐 | AWQ 吞吐 | AWQ 相对 BF16 |
|---:|---:|---:|---:|
| 1 | 167.29 tok/s | 220.30 tok/s | **+31.7%** |
| 32 | 3948.35 tok/s | 3186.65 tok/s | **-19.3%** |

![AWQ 相对 BF16：并发 1 赚钱，并发 32 反噬](assets/fig-awq-concurrency.png)

单请求 Mean ITL 从 5.94ms 降到 4.49ms；并发 32 时却从 7.98ms 升到 9.92ms。低并发方向与论文「Decode 吃量化」一致，但倍数远没有 TinyChat vs HF 那么夸张——基线已经强很多。高并发则直接翻脸。

> **采样说明**：这组目前只打了 conc=1 与 conc=32 两端，足以证明「会换脸」，**还不能精确标出交叉点在 4、8 还是 16**。若你要拿 AWQ 做默认部署，请在自己的到达过程上补中间档；EAGLE3 那条完整并发曲线（第六节）是同系列里采样更密的范本。

#### 3. 异常与反常识

**并发越高，量化越亏。** 直觉是「压缩总该更省」，但 batch 上去后：

1. 同一份权重被更多 token 摊薄，每 token 分摊的读带宽下降；
2. 解量化和量化 kernel 的固定开销、以及它们相对成熟 BF16 路径的效率差距，开始露头；
3. 系统从「带宽受限」滑向「计算 / kernel 效率受限」。

交叉点不在「量化准不准」，而在**瓶颈迁移**。H20 算力带宽比更低，低并发更容易从权重量化获益；换到 H100/H800，交叉点会右移或左移。

#### 4. 实践启示

- 低 QPS、在意单路延迟的服务：4bit 权重值得认真 A/B。
- 高并发打满吞吐的服务：先测交叉点，再决定是否默认 AWQ；我们这组在 conc=32 已经 -19%。
- 别用「论文 3×」做容量规划；用**你的框架 + 你的卡 + 你的并发曲线**。

**那生产 Decode 大多是打 batch 的，AWQ 是不是干脆别开？** 只看提速，是的——高并发实例上纯为吞吐开 AWQ 常是负收益，别默认开。但别忘了它还有第二本账：**容量**。4bit 权重直接省掉一半多显存，可能让模型少占卡、或给 KV 腾出空间——这本账在高并发下照样成立，只是省的是「装得下 / 少买卡」，不是「每 token 更快」。所以务实的做法是按实例分：延迟敏感 / 低并发实例为提速开；高吞吐实例默认关，除非你是为了塞下模型才用它。两本账别混着算。

### B. FlashAttention：数学不变，数据少走几趟

#### 1. 技术原理

朴素注意力会物化巨大的 \(n \times n\) 中间矩阵，写 HBM 再读回来。FlashAttention 用分块（tiling）+ 在线 softmax，把中间结果留在 SRAM，数学等价，IO 大幅下降。它省的不是注意力 FLOPs 的渐进复杂度，而是**内存墙**。

#### 2. 论文的数据 vs 我们的实测

FlashAttention 系列论文相对朴素实现常报数倍加速，并强调长序列下优势扩大；FA2/FA3 继续在不同硬件上抠 kernel。生产框架里，对手往往已是 FlashInfer / Triton 等优化后端，不会再出现「相对教学版 matmul 的 5～10×」。

我们只换 attention 后端，模型与负载固定。注意：下表是**长上下文 Prefill 主导**负载下的端到端输出吞吐与中位 TTFT，不是 Decode 稳态「每秒生成几百 token」那种数——绝对值偏小是负载形态使然，比的是**相对后端差**：

| 后端 | 4K 吞吐 | 4K 中位 TTFT | 8K 吞吐 | 8K 中位 TTFT |
|---|---:|---:|---:|---:|
| FA3 | 19.96 tok/s | 2277.36 ms | 10.40 tok/s | 3218.40 ms |
| FlashInfer | 19.27 tok/s | 2367.45 ms | 9.86 tok/s | 3559.40 ms |
| Triton | 17.67 tok/s | 2540.24 ms | 8.75 tok/s | 4057.33 ms |
| torch_native | 14.27 tok/s | 3313.93 ms | 8.45 tok/s | 4676.89 ms |

FA3 相对 torch_native，4K 吞吐 +39.9%，8K +23.1%，两档中位 TTFT 约 -31%。仍是「少搬中间结果」的故事，但量级是**框架内后端差**，不是论文海报上对朴素实现的极限差。

#### 3. 异常与反常识

序列从 4K 到 8K，FA3 相对 torch_native 的吞吐优势从 +39.9% 收到 +23.1%。可能让人意外：不是更长更该拉开差距吗？在这组 serving 负载里，TTFT/吞吐还叠了调度、采样、其他层 GEMM；attention 只是其中一块。后端 dual 很真实，但不会单调变成「序列越长，相对加速比一定越大」。

torch.compile 这一格甚至没拿到可比数字：Torch 2.11 + 当前 SGLang 下，`--enable-torch-compile` 在导入 Inductor 时 `AssertionError: duplicate template name`。可部署性本身也是账单——纸面融合收益，进不了启动流程就等于零。

#### 4. 实践启示

- 默认选成熟 attention 后端（FA3 / FlashInfer），少在生产用 torch_native「先跑起来」。
- 换后端要在真实序列长度和 batch 下测 TTFT，不要只看 kernel microbench。
- 编译融合当加分项，当依赖项前先看你的 Torch/框架组合能不能稳定启动。

> 💰 **一句话价签**：带宽墙下少读比多算划算——AWQ 的便宜只在低并发（+31.7%），并发一高就反噬（-19.3%）；attention 后端直接选成熟的（FA3/FlashInfer），别拿 torch_native 当默认。

## 四、少占：容量翻倍，不等于每个 token 立刻更快

### 1. 技术原理

少占管的是**显存里状态有多贵**：KV 池能装多少 token、能撑多大并发和多长上下文。PagedAttention 消灭预留空洞；KV 量化把每 token 状态砍半；GQA/MLA 从结构上缩小每 token KV。

关键一句：**容量不是时间**。它通过两条路径变现——更大 batch（打满）、更高前缀命中（不算）——而不是让已经在跑的那次 matmul 自动快 N 倍。

### 2. 论文的数据 vs 我们的实测

**FP8 KV。** 从 BF16 到 FP8，每 token 状态理论上约一半，池容量接近 2× 是「算术上就该如此」的结果，前提是框架真的按该 dtype 分配。

| KV dtype | KV 池 token 数 | 相对容量 |
|---|---:|---:|
| BF16 | 474,376 | 1× |
| FP8 E4M3 | 948,752 | 2× |

我们读到的启动日志是精确 2×。这次没提供校准后的 KV scaling factor，SGLang 警告默认 scale=1.0，所以账上只能写「容量 2×」，不能顺手写「精度无损」。

**MLA。** DeepSeek-V2 论文相对其基线称 KV cache 约减 **93.3%**，最大生成吞吐可到 **5.76×**（相对 DeepSeek 67B 那条对比线，不是「任意模型换 MLA 就 5.76×」）。我们用 DeepSeek-V2-Lite-Chat 做显微镜，不把它当文章主角。请先钉死一句：下面是**跨模型的系统级容量对照**（参数量、层数、每 token KV 布局均不同），**不是**同模型上「打开 MLA 开关」的 A/B，也不能写成「换 MLA 就加速 3.71×」：

| 模型 / 结构 | KV 池 token 数 | 相对 Qwen3-8B |
|---|---:|---:|
| Qwen3-8B GQA（E5） | 474,376 | 1× |
| DeepSeek-V2-Lite MLA（FlashInfer/Triton） | 1,759,061 | **约 3.71×** |
| DeepSeek-V2-Lite MLA（FlashMLA） | 1,759,040 | 约 3.71× |

3.71× 是**同卡、同 mem-fraction 下可服务 token 池**的系统级对照：层数、权重体积、每 token 布局都不同，不能写成「MLA 相对 GQA 的纯结构压缩比」，更不能和论文 93.3% 直接画等号——那是论文设定下相对 MHA 基线的结构压缩，我们这里是两款不同模型的 serving 池快照。容量账单可以横比「这张卡还能再塞多少状态」；速度账单不能直接把 3.71× 抄进 SLA。

结构红利还要 kernel 接住。固定 V2-Lite 与 Decode 负载（并发 8），只换 MLA 后端：

| 后端 | 输出吞吐 | 中位 TTFT | 中位 ITL | P99 ITL |
|---|---:|---:|---:|---:|
| FlashInfer | 932.22 tok/s | 84.29 ms | 8.44 ms | 9.04 ms |
| FlashMLA | 921.13 tok/s | 87.24 ms | 8.52 ms | 9.03 ms |
| Triton | 883.17 tok/s | 90.00 ms | 8.90 ms | 9.55 ms |

FlashInfer 相对 Triton 吞吐约 +5.6%，中位 ITL 约 -5.2%。差距个位数：有差，但不是「接不住结构」的悬崖。

长上下文曲线（FlashInfer，单并发）：

| 输入长度 | 输出吞吐 | 中位 TTFT | 中位 ITL | Mean ITL |
|---:|---:|---:|---:|---:|
| 4K | 101.83 tok/s | 207.25 ms | 4.65 ms | 4.61 ms |
| 16K | 31.51 tok/s | 1107.93 ms | 5.09 ms | 5.05 ms |
| 30K | 27.64 tok/s | 1247.63 ms | 5.65 ms | 5.60 ms |

![长上下文 Mean ITL 曲线：全注意力 vs MLA 对照](assets/fig-context-itl-curves.png)

上下文约 7.32×，Mean ITL 仅 +21.5%。Qwen3-8B 全注意力 E7 同指标：Mean ITL 6.07→8.28ms（+36.4%）。斜率都向上，MLA 对照更缓；模型不同，我们不把差值全记在 MLA 账上。

### 3. 异常与反常识

**容量 2×，延迟不会 2× 好。** FP8 KV 首先改变的是「能装多少」，不是「当前这个 token 算多快」。若并发和上下文没涨到吃满旧池，用户体感可能几乎不变——钱躺在显存余额里。

**论文 93% 压缩 ≠ 你线上池子立刻 10×。** 权重、框架预留、碎片、并行策略都会吃掉结构红利；还要有 MLA kernel，否则只是「理论状态更小」。

**更小的 KV 仍可能随长度变慢。** MLA 曲线里 4K→30K ITL 仍在涨：历史照样要读，只是每步读得更少。

### 4. 实践启示

- 上 KV 量化前先回答：瓶颈是 OOM / 并发上不去，还是单路 ITL？前者更对症。
- 选 MLA/GQA 模型是训练期就定下的结构支票；推理侧要做的是接住（kernel、页式池、调度），不是事后把 MHA「调成」MLA。
- 容量类优化的验收应包含：最大并发、最大上下文、缓存命中，而不是只跑一条短 prompt 的 tok/s。

> 💰 **一句话价签**：容量是弹药不是扳机。FP8 KV 精确 2× 池子、MLA 对照约 3.71×，但池子翻倍不等于每个 token 变快——得靠并发或命中率把它花出去，还得有 kernel 接住。

## 五、打满：把 GPU 空转的几种原因分别掐掉

### 1. 技术原理

前四个动词决定「要算多少、搬多少、存多少」；打满管的是：**干活时硬件有没有闲着**。闲的原因不止一种：

| 闲在哪 | 典型手段 | 治的是什么 |
|---|---|---|
| batch 有空位 | Continuous batching | 请求间互相等 |
| Prefill 堵 Decode | Chunked prefill / PD 分离 | 长短请求互相踩 |
| CPU 发 kernel 太慢 | CUDA Graph | 小 batch 下 launch 开销 |
| CPU 调度与 GPU 串行 | Overlap Scheduler | 跨 iteration 的调度空隙 |

CUDA Graph：把一轮相对固定的 kernel 序列录成图，回放时一次提交，避免成百上千次 launch。Overlap：GPU 算当前步时，CPU 处理上一步结果并准备下一步输入，把调度藏进计算。

![Overlap Scheduler 时序：把 CPU 调度藏进 GPU 计算](assets/fig-overlap-principle.png)

### 2. 论文的数据 vs 我们的实测

连续批处理、paged attention 的经典工作把 serving 吞吐相对静态 batch 抬了一个数量级；那是「调度范式」级别的跃迁。我们这组测的是**在已经连续批处理的框架里**，再拧 overlap / chunk / graph 这些细开关。读法上分两桶：**默认该开的**（Overlap、CUDA Graph）和**要按到达过程调的**（Chunked Prefill）——后者这组数据里还给出了负结果。

**Overlap Scheduler：**

| 并发 | 关闭吞吐 | 开启吞吐 | 开启收益 |
|---:|---:|---:|---:|
| 8 | 1134.83 tok/s | 1255.21 tok/s | **+10.6%** |
| 32 | 3573.12 tok/s | 3949.36 tok/s | **+10.5%** |

两档几乎同一答案：约 +10.5%。不像量化那样改算子成本，而是收回算子之间的调度空隙。

**CUDA Graph（同系列既有实验，旁证）：** 开图后 bs=1 每步 14.27→6.08ms，快 2.35×；估算 GPU 忙时占比 38%→92%。算子没变快，省掉的是 host 发射间隙。这组数字**不与本文其余表逐行同一次消融**，方向可参考，容量规划请在你的 SGLang / 形状组合上复测。

**Chunked Prefill：** 我们原以为关闭切块会让长 Prefill 堵住 Decode、P99 ITL 恶化：

| Chunk 大小 | 输出吞吐 | P99 ITL |
|---:|---:|---:|
| 关闭（-1） | 422.74 tok/s | 442.69 ms |
| 8192 | 422.15 tok/s | 452.06 ms |
| 2048 | 416.07 tok/s | 479.62 ms |
| 512 | 394.95 tok/s | 513.86 ms |

关闭反而最好；512 小块相对关闭吞吐 -6.6%，P99 ITL +16.1%。

### 3. 异常与反常识

**Chunked prefill「本该保护尾延迟」，这组数据里没发生。** 负结果往往比正结果刺眼：说明该负载没有制造「长 Prefill 饿死 Decode」的到达形态；切得过碎的调度税却先到了。

**Overlap 在 conc=8 和 32 收益几乎一样。** 直觉或许觉得越忙越好藏，或越闲越好藏——我们看到的是一笔相对稳定的调度税，大约一成吞吐，对中等和高并发都在。

**CUDA Graph 和 Overlap 不是互相替代。** 一个治 launch，一个治 schedule；可以两笔钱同时在。

### 4. 实践启示

- 默认打开 Overlap / CUDA Graph（框架支持且形状稳定时），它们是「捡在地上的一成」。
- 调 chunk size 不要玄学：用真实到达过程压 P99，而不是只扫几个整数。
- 若线上已是 PD 分离，单机 chunked prefill 的优先级会下降——瓶颈画像变了。

> 💰 **一句话价签**：捡在地上的一成。算子不变快，收回的是它们之间的空隙（Overlap ≈ +10.5%，CUDA Graph 2.35×）；框架支持、形状稳定就默认开。chunk 大小别玄学调，用真实到达过程压 P99。

## 六、破串行：投机解码和 batching 在抢同一份闲置算力

### 1. 技术原理

前五个动词优化「每一轮多快」；破串行攻击**轮数**。投机解码用便宜草稿（小模型或 EAGLE 头）连续猜多个 token，大模型一次前向并行验证。数学上可构造为与自回归采样同分布；猜对几个就前进几步。

它为何在 Decode 可行？小 batch 下 Decode 常受带宽限制：**验证 5 个 token 和验证 1 个，权重往往只搬一遍**，多花的是闲置算力。于是投机和 batching 花的是同一笔余量——batching 拿去服务更多请求，投机拿去赌同一条请求的未来。

EAGLE3 相对早期 EAGLE，加强多特征融合与直接 token 预测等，论文侧重抬高接受长度与加速比。

![投机解码原理：草稿猜测 + 大模型一次验证](assets/fig-speculative-principle.png)

### 2. 论文的数据 vs 我们的实测

EAGLE-3 论文在学术评测、偏 **batch size 1** 的设定下，报过约 **3.0×～6.5×** 相对朴素自回归的加速（任务相关，代码生成等模板性强的任务更高）；相对 EAGLE-2 大约还有一截提升。也有框架侧数字提到较大 batch 时仍可能有吞吐收益，但强烈依赖实现与负载。

我们在 H20 上扫并发，draft 为 Qwen3-8B 的 EAGLE3 路径：

| 并发 | 普通 Decode | EAGLE3 | 加速比 |
|---:|---:|---:|---:|
| 1 | 168.90 tok/s | 316.56 tok/s | **1.87×** |
| 4 | 631.38 tok/s | 583.44 tok/s | **0.92×** |
| 8 | 1094.40 tok/s | 651.03 tok/s | **0.59×** |
| 16 | 1789.69 tok/s | 713.70 tok/s | **0.40×** |
| 32 | 2633.27 tok/s | 758.88 tok/s | **0.29×** |

![EAGLE3 加速比随并发变化：交叉点在 1～4](assets/fig-eagle3-concurrency-curve.png)

单请求 1.87×，远低于论文上限 6.5×——模型、任务、接受率、框架开销都不同，且我们的基线已是生产路径而非最慢自回归。更刺眼的是：**并发 4 已转负**，之后加速比单边下跌。

### 3. 异常与反常识

**「加速算法」在高并发变成减速器。** 这是整组实验最陡的曲线，也是最值得记住的反常识：

1. 低并发：算力闲、带宽紧 → 一次验证多 token 划算；
2. 高并发：batching 已吃掉闲置算力 → 草稿前向、树状验证、拒绝回滚都在和正式请求抢 SM 与显存；
3. 接受率若一般，拒绝越多越亏。

所以论文 bs=1 的 6.5× 和线上 conc=32 的 0.29× 可以同时为真，并不矛盾——它们测量的是两种世界。

### 4. 实践启示

- 按 SLA 选型：在意**单路延迟**、QPS 不高 → 认真开投机；KPI 是**集群总吞吐** → 先画自己的并发交叉点再决定默认开不开。
- 接受率是一等公民：草稿再长，第一个 token 总被拒，就只是在交验证税。
- 投机与「再堆并发」可能互斥；容量规划不要默认两者增益相乘。

**同样地，Decode 常年打满的高吞吐实例，静态开 EAGLE3 基本是负的**——这时闲置算力已被 batching 吃光，草稿和验证只会抢正经请求的资源。但它不像 AWQ 还有容量这本副账：投机纯粹换延迟，高并发下没有「另开一本还成立」的理由。所以两条路——要么把它限定在低并发 / 延迟优先的实例，要么用**随 batch 自适应**的调度（并发低时开、并发高时缩短草稿甚至关掉）。真实流量有波峰波谷，「按当前 batch 动态开关」通常比「全局一刀切」更值钱。

> 💰 **一句话价签**：低并发的利器、高并发的鸡肋。它和 batching 抢同一份闲置算力——并发 1 拿到 1.87×，并发 4 就转负，谁先把闲置算力花完谁赢。接受率是一等公民。

## 七、跑分卫生：第一轮数据可能测的是初始化，不是模型

我们特意保留冷启动对照：server 刚 ready 就压并发 32，然后原地重复同一命令。

| 状态 | 输出吞吐 | 中位 TTFT | P99 ITL |
|---|---:|---:|---:|
| 冷启动第一轮 | 3624.23 tok/s | 412.71 ms | 8.90 ms |
| 原地第二轮 | 3951.82 tok/s | 66.40 ms | 8.74 ms |

第二轮吞吐 +9.0%，中位 TTFT -83.9%。ITL 稳态差不多，税主要在首轮。server ready ≠ lazy JIT / Triton autotune / 缓存路径都热完。

这次所有正式 A/B 前都丢弃一轮 warmup。否则「巨大优化收益」可能只是左右两组落在不同热身阶段——那是方法错误，不是技术胜利。

## 八、把账单重新放回六个动词

数字会过时，下面五条更耐用。

**第一，先找墙，再选优化。**  
Prefill 撞算力墙时，少算（如 FP8）更值钱；Decode 撞带宽墙时，少搬（如 AWQ）在低并发值钱、高并发可能反噬。同一张卡上，阶段变了，最优动词就变了。

> 一个常见的误读要挡一下：「Prefill 用少算、Decode 用少搬」说的是**每个动词在哪个阶段兑现收益**，不是让你给 Prefill 挂 FP8 权重、给 Decode 挂 AWQ 权重。权重量化格式是模型加载时定死的**一个全局选择**——就算做了 PD 分离，Prefill 和 Decode 两个节点加载的也是同一份模型，不会一边 FP8 一边 AWQ。真正按阶段分化的是这些：注意力 kernel（prefill kernel 本就和 decode kernel 不同）、调度与 batch 策略、要不要开投机、以及**硬件选型**（Prefill 放算力强的卡、Decode 放带宽强的卡）。所以两面墙指导的是「这台机器该往哪个方向调、该配什么卡」，而不是「同一份权重切两种量化」。

**第二，容量必须通过并发或命中率变现。**  
少占（FP8 KV、MLA 一类）先改的是「能装多少」，不是「当前 token 自动快 N 倍」。少占是弹药，打满和不算才是扳机；结构红利还要 kernel 接住。

**第三，不同优化会抢同一份余量。**  
投机解码与 batching 都在花 Decode 闲置算力。增益不能默认连乘。

**第四，论文倍数要连实验设定一起读。**  
海报上的 ×N 各自对照基线、batch、框架都不同。我们的贡献不是「打假」，而是给出**同一套 H20 + SGLang 生产路径**上的可横比价签，并标出换脸边界。

**第五，负结果也要入账。**  
Chunked Prefill 未改善这组尾延迟；torch.compile 启动失败；高并发 AWQ / EAGLE 转负。删掉它们文章更顺，工程判断会更差。

把这五条压成一件随身工具——**下次再看到一个加速比，别急着信，先对三次账**：

1. **它的数据出自哪个世界？** 论文测的 batch、序列、阶段是什么，和你线上像不像？batch=1 的 6.5× 不是给并发 32 开的支票。
2. **它省的是哪种资源？** 算力、带宽、容量、还是串行轮数——你现在缺的，正好是它省的这一种吗？省一样你不缺的东西，墙上的钟不会动。
3. **它的换脸边界在哪？** 并发拉高、上下文拉长、和别的优化同时开，这个价签会不会缩水甚至转负？把这条写进验收，而不是等上线才发现。

三次对完，这个数字能不能进你的容量规划，基本就清楚了。

上一篇的六个动词不是六个互斥抽屉，而是六本账：省了多少计算、搬运、容量、空隙或串行轮数，又额外花了什么。真正能迁移到下一张卡、下一个模型的，不是「某技术快多少倍」，而是知道这倍数从哪笔闲置资源里来，以及那笔资源什么时候会被别的优化先花掉。

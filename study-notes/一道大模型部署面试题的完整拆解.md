# 一道大模型部署面试题的完整拆解：如果让你部署 GLM-5.2

> 这是一篇写给想搞懂大模型推理部署每一个细节的工程师的文章。我们不背公式，不算花账，每一节都追问"为什么"。

---

## 0. 题目与约束——面试官只给了一句话

面试官的原题非常简单：

> "我们要部署 GLM-5.2，你出一个方案。"

就这一句。没有硬件预算，没有延迟要求，没有并发量，没有上下文长度。什么都没有。

**这恰恰是这道题最妙的地方。** 它考察的不是"你会不会敲命令"，而是你能不能从一个模糊需求出发，通过反向提问和合理假设，把问题收敛成一个可计算的工程问题。

### 0.1 第一步：反向提问——把模糊需求变成可计算的约束

一个合格的候选人，第一反应不应该是直接讲 TP=8，而是反问。以下是我认为必须澄清的几个问题，以及为什么每个问题都重要：

**Q1: 这个服务的场景是什么？**

这决定了整个优化方向。是 chatbot（短 prompt、短 completion、延迟敏感）？是代码助手（长 prompt、短 completion、读多写少）？还是批量评估（离线、吞吐优先）？

我假设面试官回答："代码助手，对标 Cursor。"

→ 这意味着：**读多写少**，prefill 计算量远大于 decode。后续的瓶颈预判、chunked prefill 决策都以此为锚点。

**Q2: 硬件预算？**

这决定了并行策略的上下界。单机 8 卡和多机 64 卡是完全不同的方案。

我假设面试官回答："先按单机 8 卡规划，GPU 型号你定。"

→ 我需要自己选卡。2026 年的主流选项：H200（141GB）、B200（180GB）、H100（80GB）。选 H200 是合理的中间值——显存够大、生态成熟、成本可控。**选卡本身就是一个 trade-off 判断。**

**Q3: 目标上下文长度？**

GLM-5.2 支持 1M 上下文，但 1M 的 KV cache 和 prefill 延迟都是巨大的。实际部署通常取一个合理值。

我假设面试官回答："希望尽量长，至少 128K。"

→ 我取 256K 作为设计目标——在 8×H200 上可行，且是 128K 的两倍，有竞争力。1M 上下文在 8 卡上偏紧，作为 stretch goal。

**Q4: 并发量和延迟 SLA？**

这决定了 batch size 和显存分配策略。

我假设面试官回答："初期 20-30 并发，TTFT 不超过 2 秒，ITL 不超过 100ms。"

→ 取 32 并发作为设计值。TTFT 2s 和 ITL 100ms 是代码助手场景的常见 SLA——用户输入一段代码上下文后等 2 秒看到第一个 token 是可以接受的，但每个 token 之间的间隔不能超过 100ms，否则感觉卡顿。

**Q5: 精度要求？**

代码生成对精度敏感，INT4 量化在 SWE-bench 这类任务上会有可感知的质量下降。

我假设面试官回答："至少 FP8。"

→ 排除 INT4，FP8 是精度和显存的平衡点。H200 的 Hopper 架构原生支持 FP8 矩阵运算，没有解量化开销。

### 0.2 汇总：我自己定义的约束

经过以上反问和合理假设，我把模糊需求收敛为以下约束表。**注意：这些约束是我自己推导出来的，不是面试官给的。** 在面试中，你应该把每个假设的理由讲清楚——面试官可能会 challenge 你的假设，但只要你逻辑自洽，这就是加分项。

| 维度 | 约束 | 来源 |
|---|---|---|
| 模型 | GLM-5.2，744B 总参数，40B 激活（MoE），1M 原生上下文 | 题目给定 |
| 硬件 | 单机 8×H200（141GB × 8 = 1128 GB 总显存） | 我选的，理由：显存/成本/生态的平衡点 |
| 场景 | 代码助手，在线 serving，读多写少 | 反问 Q1 |
| 并发 | 32 个并发请求 | 反问 Q4，取合理中值 |
| 上下文 | 设计目标 256K（模型支持 1M） | 反问 Q3，128K 的两倍，8 卡可行 |
| 延迟 | TTFT < 2s，ITL < 100ms | 反问 Q4，代码助手场景常见 SLA |
| 精度 | FP8 | 反问 Q5，精度与显存的平衡点 |

好，约束有了。现在从零开始推导。

## 1. 显存账本——钱花在哪了

部署大模型，显存是硬约束。显存主要花在三块：**权重、KV cache、激活/临时张量**。我们一笔一笔算。

### 1.1 模型架构速览

先看一眼 GLM-5.2 的 config.json（来自 HuggingFace `zai-org/GLM-5.2`）：

```
hidden_size: 6144
num_hidden_layers: 78
num_attention_heads: 64
num_key_value_heads: 64
kv_lora_rank: 512          # MLA KV 压缩维度
q_lora_rank: 2048          # MLA Q 压缩维度
qk_nope_head_dim: 128      # Q/K 的非 RoPE 部分维度
qk_rope_head_dim: 64       # Q/K 的解耦 RoPE 维度
v_head_dim: 256            # V 的每个 head 维度
intermediate_size: 12288   # 前 3 层 dense FFN
moe_intermediate_size: 2048  # 每个 expert 的 FFN
n_routed_experts: 256
n_shared_experts: 1
num_experts_per_tok: 8
first_k_dense_replace: 3   # 前 3 层是 dense，后面 75 层是 MoE
max_position_embeddings: 1048576  # 1M 上下文
vocab_size: 154880
```

关键信息：
- **MLA（Multi-head Latent Attention）**：KV 被压缩到 `kv_lora_rank=512` 维，外加解耦的 RoPE 部分 `qk_rope_head_dim=64` 维。这是显存账本里最大的变量。
- **DSA（DeepSeek Sparse Attention）**：长上下文时只对 Top-2048 个 token 做完整注意力计算，IndexShare 机制每 4 层共享索引器，1M 上下文下每 token 计算量降低 2.9 倍。
- **MTP（Multi-Token Prediction）**：1 个额外预测头，支持投机解码。

### 1.2 权重显存

这是最直观的一笔账：

| 精度 | 每参数字节数 | 744B 权重占用 |
|---|---|---|
| BF16 | 2 bytes | 744 × 2 = **1488 GB** |
| FP8 | 1 byte | 744 × 1 = **744 GB** |
| INT4 | 0.5 bytes | 744 × 0.5 = **372 GB** |

BF16 直接出局——1488 GB 远超 1128 GB 总显存，单卡放不下，8 卡也放不下（还有 KV cache 和激活没算）。

**FP8 是这道题的唯一可行起点**：744 GB 权重占 8 卡总显存的 66%，还剩约 384 GB 给 KV cache 和激活。

> 为什么不是 INT4？代码生成对精度敏感，INT4 量化在 SWE-bench 这类任务上会有可感知的质量下降。FP8 是当前生产环境的主流选择——H200 的 Hopper 架构原生支持 FP8 矩阵运算，没有额外的解量化开销。

### 1.3 MLA 深度拆解——KV Cache 为什么这么小

这是全文最核心的一节。如果不理解 MLA 的计算图，你不仅会算错 KV cache 的大小，还会算错 attention 的计算量。

#### 1.3.1 传统 MHA 的问题

在标准多头注意力中，每个 token 的每层需要存储完整的 K 和 V：

```
K: num_kv_heads × head_dim = 64 × 192 = 12,288 个元素
V: 同样 12,288 个元素
每层每 token: (12,288 + 12,288) × 2 bytes = 48 KB
78 层: 78 × 48 KB ≈ 3.74 MB/token
256K 上下文: 256,000 × 3.74 MB ≈ 958 GB
```

958 GB 只用于 KV cache！加上 744 GB 权重 = 1702 GB，远超 1128 GB。**传统注意力根本不可行。**

#### 1.3.2 MLA 的完整计算图

MLA 的核心思路是把 K 和 V 压缩到一个低维潜在空间，然后在注意力计算时再展开。但展开不是"解压回完整 K/V 再做注意力"——那样就没有省计算了。MLA 用了一个关键的**吸收（absorption）优化**，让注意力直接在压缩空间里做。

下面是完整的 MLA 计算图（以 GLM-5.2 为例）：

**Step 1: 输入投影到潜在空间**

```
输入 hidden_states: [batch, seq_len, 6144]

↓ fused_qkv_a_proj_with_mqa (一个联合线性层)

输出 latent: [batch, seq_len, q_lora_rank + kv_lora_rank + qk_rope_head_dim]
          = [batch, seq_len, 2048 + 512 + 64]
          = [batch, seq_len, 2624]

拆分为三部分:
  q_latent:  [batch, seq_len, 2048]   ← Q 的压缩表示
  k_nope:    [batch, seq_len, 512]    ← K 的非 RoPE 部分（压缩表示）
  k_pe:      [batch, seq_len, 64]     ← K 的 RoPE 部分（不压缩，保留位置信息）
```

注意：`k_nope` 和 `k_pe` 就是 KV cache 里实际存储的内容。**没有"完整的 K"，只有压缩后的 K。**

**Step 2: Q 的展开**

```
q_latent [batch, seq_len, 2048]
  ↓ q_a_layernorm (RMSNorm)
  ↓ q_b_proj (2048 → num_heads × qk_head_dim = 64 × 192 = 12288)
  ↓ reshape

q: [batch, seq_len, 64, 192]
  拆分为:
    q_nope: [batch, seq_len, 64, 128]  ← 非 RoPE 部分
    q_pe:   [batch, seq_len, 64, 64]   ← RoPE 部分
```

**Step 3: 吸收优化（核心）——Q 与 K 在压缩空间做注意力**

这是 MLA 最精妙的设计。传统做法是先把 `k_nope`（512 维）通过 `kv_b_proj` 展开到完整的 K（64 heads × 128 dims = 8192 维），然后和 Q 做注意力。但 MLA 把 `kv_b_proj` 的 K 部分**吸收到了 Q 的投影里**：

```
# 传统做法（不做吸收）:
K_full = k_nope @ W_K_up   # [batch, seq_len, 512] @ [512, 64×128] → [batch, seq_len, 64, 128]
scores = Q_nope @ K_full^T  # [batch, seq_len, 64, 128] @ [batch, seq_len, 128, 64]

# MLA 吸收做法:
Q_absorbed = Q_nope @ W_K_up  # [batch, seq_len, 64, 128] @ [128, 64, 512] → [batch, seq_len, 64, 512]
scores = Q_absorbed @ k_nope^T  # [batch, seq_len, 64, 512] @ [batch, seq_len, 512]
```

注意发生了什么：
- 传统做法：`K_full` 是 `[seq_len, 64, 128]`，KV cache 要存 8192 个元素
- MLA 做法：`k_nope` 是 `[seq_len, 512]`，KV cache 只存 512 个元素，**压缩了 16 倍**
- 注意力计算量：传统是 `64×128` 的内积，MLA 是 `512` 的内积——**计算量也减少了**

> 在 SGLang 的实际代码中，这个吸收通过 `w_kc` 矩阵实现：`q_nope_out = q_nope @ w_kc`，其中 `w_kc` 的形状是 `[num_heads, qk_nope_head_dim, kv_lora_rank]` = `[64, 128, 512]`。这个 `w_kc` 就是 `kv_b_proj` 中负责 K 上投影的那部分权重，在模型加载时就被吸收进了 Q 的计算路径。

**Step 4: 注意力计算（在压缩空间）**

```
# Q 的压缩空间表示（已经吸收了 W_K_up）
Q_absorbed: [batch, seq_len, 64, 512]

# K 的压缩空间表示（直接从 KV cache 读取）
k_nope: [batch, seq_len, 512]

# 注意力分数
scores = Q_absorbed @ k_nope^T / sqrt(512 + 64)
       = [batch, seq_len, 64, 512] @ [batch, seq_len, 512]
       = [batch, seq_len, 64]

# 加上 RoPE 部分的分数
scores_rope = q_pe @ k_pe^T / sqrt(576)
scores = scores + scores_rope

# softmax + 加权求和（也在压缩空间）
attn_weights = softmax(scores)
attn_output = attn_weights @ k_nope  # [batch, seq_len, 64] @ [batch, seq_len, 512]
            = [batch, seq_len, 64, 512]
```

**Step 5: V 的上投影——v_head_dim 的作用**

注意力输出是 `[batch, seq_len, 64, 512]`（64 个 head，每个 head 512 维的压缩表示）。但最终输出需要回到 `hidden_size=6144`。这里需要两步：

```
attn_output: [batch, seq_len, 64, 512]

↓ w_vc (V 上投影，kv_b_proj 中负责 V 的那部分)
  形状: [num_heads, kv_lora_rank, v_head_dim] = [64, 512, 256]

attn_v: [batch, seq_len, 64, 256]

↓ flatten + o_proj
  flatten: [batch, seq_len, 64×256] = [batch, seq_len, 16384]
  o_proj:  [batch, seq_len, 16384] @ [16384, 6144] → [batch, seq_len, 6144]
```

**`v_head_dim=256` 就是 V 投影后每个 head 的维度。** 它不是 KV cache 的一部分——KV cache 只存 `k_nope`（512 维）和 `k_pe`（64 维）。`v_head_dim` 只影响 `w_vc` 和 `o_proj` 的权重形状，以及这两步矩阵乘法的计算量。

#### 1.3.3 KV Cache 的精确计算

现在我们可以精确计算 KV cache 了。KV cache 存储的是：

```
每层每 token:
  k_nope: kv_lora_rank = 512 个元素
  k_pe:   qk_rope_head_dim = 64 个元素
  总计: 512 + 64 = 576 个元素
```

```
每层每 token (BF16): 576 × 2 bytes = 1,152 bytes ≈ 1.125 KB
78 层: 78 × 1.125 KB ≈ 87.75 KB/token
```

对比传统 MHA 的 3.74 MB/token，**MLA 把 KV cache 压缩了约 43 倍**。

不同上下文长度的 KV cache（BF16）：

| 上下文长度 | KV Cache (MLA, BF16) |
|---|---|
| 8K | 8,192 × 87.75 KB ≈ **0.69 GB** |
| 32K | 32,768 × 87.75 KB ≈ **2.74 GB** |
| 128K | 131,072 × 87.75 KB ≈ **10.97 GB** |
| 256K | 262,144 × 87.75 KB ≈ **21.94 GB** |
| 1M | 1,048,576 × 87.75 KB ≈ **87.75 GB** |

**这就是 MLA 的威力：1M 上下文的 KV cache 只需要 88 GB。** 如果没有 MLA，这个数字是 ~3.6 TB，完全不可行。

> **重要修正：KV cache 是 per-GPU 分片的。** 在 TP=8 下，每张卡只持有 `1/8` 的 KV cache（因为 attention head 被切分了）。所以上面的数字需要除以 8：
>
> | 上下文长度 | KV Cache per GPU (MLA, BF16, TP=8) |
> |---|---|
> | 256K | 21.94 / 8 ≈ **2.74 GB** |
> | 1M | 87.75 / 8 ≈ **10.97 GB** |
>
> 这个修正非常重要——之前我算的是全局 KV cache，但显存账本应该按 per-GPU 来算。

### 1.4 激活与临时张量——这笔账怎么算

这是最难精确估算的一笔账，因为激活显存取决于 batch size、序列长度、模型架构、框架实现等多个变量。但我们可以从第一性原理出发，分几个层次来估算。

#### 1.4.1 激活显存的来源

一次前向传播中，以下内容需要占用显存：

**a) 残差连接（residual）**

每层需要保存输入 hidden_states 用于残差加法。对于 78 层模型，如果不用重计算（recomputation），需要保存 78 份。

```
每份: batch × seq_len × hidden_size × dtype_size
chunked prefill 下 batch 很小（比如 chunk_size=8192，batch=1）:
  8192 × 6144 × 2 bytes ≈ 96 MB
```

但实际上推理框架不会保存所有 78 层的残差——推理是一次性前向，不需要反向传播，所以**残差不需要长期保存**。每个 layer 的输入用完即弃。

**b) 中间激活（intermediate activations）**

每个 transformer 层内部会产生中间张量：
- Attention 的 Q、K、V 投影结果
- Attention scores 矩阵（`batch × num_heads × seq_len × seq_len`，这是大头）
- FFN/MoE 的中间结果

Attention scores 矩阵是最大的单块激活：

```
# Prefill 阶段（chunked，chunk_size=8192）:
scores: batch × num_heads × chunk_size × chunk_size × 2 bytes
      = 1 × 64 × 8192 × 8192 × 2 bytes ≈ 8 GB

# Decode 阶段（每次 1 个新 token）:
scores: batch × num_heads × 1 × seq_len × 2 bytes
      = 32 × 64 × 1 × 32768 × 2 bytes ≈ 128 MB
```

可以看到，prefill 的 attention scores 是激活显存的主要消耗者。**Chunked prefill 通过限制 chunk_size 来控制这个峰值。**

**c) MoE 的 all-to-all 通信缓冲区**

GLM-5.2 有 256 个 expert，每个 token 激活 8 个。在 MoE 层，token 需要被路由到不同的 expert，这需要 all-to-all 通信（如果用了 EP）或本地重排（TP 下在卡内完成）。

在 TP=8 且 EP=1 的配置下，所有 expert 权重都在每张卡上（被 TP 切分），所以 MoE 的路由是本地操作，不需要 all-to-all 通信缓冲区。**这省了一大笔显存。**

#### 1.4.2 框架开销

框架开销包括：
- **CUDA context**：~1-2 GB per GPU（固定开销）
- **cuBLAS/cuDNN workspace**：~500 MB - 1 GB
- **NCCL 通信缓冲区**：TP=8 下约 200-500 MB
- **Python/PyTorch 运行时**：~500 MB - 1 GB
- **CUDA Graph 重放缓冲区**：如果启用了 CUDA Graph（SGLang 默认启用），需要额外的显存来存储 graph 的输入输出 buffer

SGLang 通过 `--mem-fraction-static` 来管理这些开销。这个参数的含义是：**总显存中，用于静态分配（权重 + KV cache pool + 框架开销）的比例**。剩下的部分留给动态激活。

```
总显存 per GPU: 141 GB
mem_fraction_static = 0.85 → 静态池: 141 × 0.85 ≈ 120 GB
动态激活可用: 141 × 0.15 ≈ 21 GB
```

#### 1.4.3 实际估算

综合以上，对于 chunked prefill（chunk_size=8192）、32 并发的 decode：

| 项目 | Per-GPU 估算 | 说明 |
|---|---|---|
| CUDA context + 框架 | ~3 GB | 固定开销 |
| CUDA Graph buffer | ~2 GB | 取决于 graph 数量 |
| 峰值激活（prefill chunk） | ~8 GB | attention scores 为主 |
| NCCL 缓冲区 | ~0.5 GB | TP all-reduce |
| **激活 + 框架合计** | **~13.5 GB** | |

注意：这个数字远小于我之前估算的 150-250 GB（那是全局的、未分片的、未考虑 chunked prefill 的粗略估计）。在 TP=8 分片 + chunked prefill 控制峰值后，per-GPU 的激活开销是可控的。

### 1.5 总账——Per-GPU 视角

这是修正后的显存账本（TP=8，FP8 权重，FP8 KV cache，256K 上下文，32 并发，平均上下文 32K）：

| 项目 | Per-GPU 估算 |
|---|---|
| 权重 (FP8, TP=8) | 744 / 8 = **93 GB** |
| KV Cache (平均 32K × 32, FP8, TP=8) | 2.74 / 2 × 32 / 8 ≈ **5.5 GB** |
| KV Cache 峰值缓冲 | ~5 GB |
| 激活 + 框架开销 | ~14 GB |
| **Per-GPU 总计** | **~117.5 GB / 141 GB** |

**结论：8×H200 可以跑，per-GPU 利用率约 83%，有约 23 GB 的余量。** 这个余量可以用来：
- 支持更长的峰值上下文（少数请求到 256K）
- 开启投机解码（MTP 头的额外显存）
- 吸收 CUDA Graph 的额外开销

## 2. 并行切分决策——TP、PP、EP 怎么选

### 2.1 单卡放不下 → 必须 TP

一张 H200 141 GB，FP8 权重 744 GB。最少需要 `ceil(744/141) = 6` 张卡来放权重。加上 KV cache 和激活，**8 卡全用上**。

### 2.2 TP = 8，PP = 1，EP = 1

对于单机 8 卡，最自然的方案是 **TP=8**（Tensor Parallelism），把每一层的权重切到 8 张卡上。

**为什么不用 PP（Pipeline Parallelism）？**

PP 把不同层放到不同卡上，好处是减少了单卡的通信量（不需要每层都做 all-reduce），坏处是有"气泡"（pipeline bubble）——前面的卡在算的时候后面的卡在等。对于在线 serving 这种延迟敏感的场景，PP 的气泡会直接反映为更高的 TTFT。

**单机 8 卡，TP=8 是最优解：**
- 每张卡持有 1/8 的权重 = 744/8 = 93 GB
- NVLink 互联带宽 900 GB/s（H200），TP 的 all-reduce 通信开销可控
- 没有 PP 气泡

### 2.3 TP vs EP 对 Expert 的切法——两种完全不同的思路

这是面试中很容易被追问的细节。在讲通信量之前，先搞清楚 TP 和 EP 到底是怎么切 expert 权重的。

#### 2.3.1 TP 切法：每张卡持有每个 Expert 的 1/8 切片

```
Expert 0 的 gate_proj 权重矩阵: [hidden_size, moe_intermediate_size] = [6144, 2048]

TP=8 按列切分:
  GPU 0: Expert 0 的 [6144, 0:256]    ← 前 256 列
  GPU 1: Expert 0 的 [6144, 256:512]  ← 256-511 列
  ...
  GPU 7: Expert 0 的 [6144, 1792:2048] ← 最后 256 列

关键：每张卡持有全部 256 个 Expert，但每个 Expert 只持有 1/8 的权重切片。
```

前向时：一个 token 激活了 Expert 3、17、42... 共 8 个 expert。8 张 GPU **同时**计算各自持有的这 8 个 expert 的 1/8 切片，然后 **all-reduce** 把 8 份部分结果拼成完整输出。

#### 2.3.2 EP 切法：每张卡持有完整的一部分 Expert

```
EP=8 按 Expert 分桶:
  GPU 0: Expert 0-31  的完整权重（每个 Expert [6144, 2048] 全量，不切）
  GPU 1: Expert 32-63 的完整权重
  ...
  GPU 7: Expert 224-255 的完整权重

关键：每张卡只持有 32 个 Expert，但每个 Expert 是完整的、未切分的。
```

前向时：一个 token 激活了 Expert 3、17、42... 如果 Expert 3 在 GPU 0、Expert 17 在 GPU 0、Expert 42 在 GPU 1...那么 token 通过 **all-to-all dispatch** 被发送到 GPU 0 和 GPU 1，各自独立完成完整计算，再通过 **all-to-all combine** 把结果送回原 GPU。

#### 2.3.3 权重显存对比——TP 和 EP 是一样的

这是很多人（包括之前的我）容易搞错的地方。算一下 per-GPU 的 expert 权重：

```
GLM-5.2 的 expert 权重总量:
  单层 256 experts: 256 × 6144 × 2048 × 3 ≈ 9.66B 参数
  75 层 MoE:        75 × 9.66B ≈ 724.5B 参数
  + shared expert:  75 × 37.7M ≈ 2.8B
  + 3 层 dense FFN: ~5B
  + attention 权重: ~12B
  ─────────────────────────────
  总计:             ≈ 744B

TP=8 下 per-GPU expert 权重:
  724.5B / 8 ≈ 90.6B  ← 每卡持有 256 个 expert × 1/8 切片

EP=8 下 per-GPU expert 权重:
  724.5B / 8 ≈ 90.6B  ← 每卡持有 32 个完整 expert

结论：per-GPU 的 expert 权重存储量完全相同！
```

**EP 不省权重显存。** 它的价值不在显存，而在通信模式。

#### 2.3.4 通信量对比

**AllReduce（TP 使用）**

```
每层 2 次 all-reduce（attention 输出 + FFN/MoE 输出）
每次: 2 × (tp_size - 1) / tp_size × 数据量
对于 hidden_size=6144, BF16:
  数据量 = batch × seq_len × 6144 × 2 bytes
  decode (batch=32, seq_len=1): 32 × 6144 × 2 = 384 KB
  通信量 ≈ 2 × 7/8 × 384 KB ≈ 672 KB per all-reduce

总通信量（78 层，每层 2 次）:
  78 × 2 × 672 KB ≈ 105 MB

在 NVLink 900 GB/s 下:
  105 MB / 900 GB/s ≈ 0.12 ms
```

**AllToAll（EP 使用）**

```
每个 MoE 层 2 次 all-to-all（dispatch + combine）
dispatch: 每个 token 发送到 top-k 个 expert
  数据量 = batch × seq_len × hidden_size × top_k / num_experts × num_gpus
         = 32 × 1 × 6144 × 8 / 256 × 8 × 2 bytes ≈ 96 KB
combine: 把 expert 输出收集回来，同样 96 KB

总通信量（75 个 MoE 层，每层 2 次）:
  75 × 2 × 2 × 96 KB ≈ 28.8 MB

在 NVLink 900 GB/s 下:
  28.8 MB / 900 GB/s ≈ 0.03 ms
```

**等等，AllToAll 的通信量看起来更小？为什么说 AllReduce 更高效？**

关键不在于总通信量，而在于**通信模式对计算的影响**：

1. **AllReduce 可以与计算重叠**。在 TP 中，每张卡独立计算自己那部分，all-reduce 只发生在最后汇总结果时。而且 NVLink 的 all-reduce 可以通过 ring/halving-doubling 算法流水线化，与下一层的计算重叠。

2. **AllToAll 破坏了数据局部性**。在 EP 中，token 需要跨卡移动——这意味着每张卡需要为"可能到来的 token"预留显存和计算资源。而且 all-to-all 的 dispatch 模式意味着每张卡都要和所有其他卡通信，建立连接的开销更大。

3. **EP 的真正价值在跨节点**。当你有 64 张卡分布在 8 个节点上时，节点间的通信带宽（如 InfiniBand 400 GB/s）远低于节点内的 NVLink（900 GB/s）。这时 EP 把 expert 权重分散到不同节点，虽然引入了跨节点的 all-to-all，但避免了跨节点的 TP all-reduce（后者需要在每个 layer 都做）。这才是 EP 的正确使用场景。

4. **实际生产中的混合策略**。大模型部署通常不会纯用 EP 或纯用 TP，而是 **TP + EP 混合**。比如 64 卡部署：节点内 TP=8（利用 NVLink 高速 all-reduce），节点间 EP=8（利用 all-to-all 避免跨节点 all-reduce）。这样每张卡既持有 expert 的 1/8 切片（TP），又只持有 1/8 的 expert（EP），per-GPU 权重 = 724.5B / 64 ≈ 11.3B。

**结论：单机 8 卡，TP=8 是最优解。EP 不上。**

### 2.4 最终并行方案

```
TP=8, PP=1, EP=1
每卡权重: 93 GB (FP8)
每卡 KV Cache: ~10.5 GB (平均)
每卡激活+框架: ~14 GB
每卡总计: ~117.5 GB / 141 GB  # 利用率 83%，有余量
```

## 3. 推理优化选项——还能省多少

### 3.1 量化路径与混合精度

**权重量化 vs KV Cache 量化 vs 激活精度——它们是三件独立的事。**

在实际推理框架（如 SGLang）中，这三者的精度是独立配置的：

| 组件 | 精度选项 | 说明 |
|---|---|---|
| 权重 | FP8 / BF16 / INT4 | 模型加载时的精度，`--dtype` 或 `--quantization` |
| KV Cache | FP8 / BF16 | 存储时的精度，`--kv-cache-dtype fp8_e4m3` |
| 激活（计算） | BF16 | 前向传播中的中间张量精度 |

**权重是 FP8，KV cache 是 FP8，但激活计算是 BF16。** 这不是矛盾——这是混合精度推理的标准做法：

```
# 矩阵乘法: FP8 权重 × BF16 激活 → BF16 输出
# H200 的 Tensor Core 原生支持这种混合精度运算

# KV cache 写入时做量化:
k_nope_bf16 (512 维) → quantize → k_nope_fp8 (512 维) → 写入 KV cache

# KV cache 读取时做反量化:
k_nope_fp8 (512 维) → dequantize → k_nope_bf16 (512 维) → 参与注意力计算
```

FP8 KV cache 的量化是**per-tensor 或 per-group 量化**，每次写入 KV cache 时在线完成。SGLang 中通过 `--kv-cache-dtype fp8_e4m3` 开启，框架会自动在 `set_mla_kv_buffer_triton_fp8_quant` 等 kernel 中完成量化。

**量化路径对比：**

| 方案 | 权重占用 | KV Cache (1M, per-GPU) | 可行性 |
|---|---|---|---|
| BF16 + BF16 KV | 186 GB/卡 | 11 GB/卡 | 不可行，权重放不下 |
| FP8 + BF16 KV | 93 GB/卡 | 11 GB/卡 | 1M 上下文可行 |
| FP8 + FP8 KV | 93 GB/卡 | 5.5 GB/卡 | **推荐**，1M 上下文宽裕 |
| INT4 + FP8 KV | 46.5 GB/卡 | 5.5 GB/卡 | 显存宽裕，但精度有损 |

**推荐路径：FP8 权重 + FP8 KV cache。** 这是当前生产环境验证过的方案，SGLang 和 vLLM 都原生支持。

### 3.2 Continuous Batching

必须开。Continuous batching 让请求可以动态加入/离开 batch，而不是等整个 batch 完成。对于代码助手这种请求长度差异大的场景，吞吐提升显著（通常 2-5x）。

SGLang 默认启用 continuous batching，不需要额外配置。

### 3.3 Chunked Prefill

**必须开。** 这是解决"长 prompt 阻塞短请求"的关键技术。

没有 chunked prefill 时，一个 256K 的 prefill 请求会独占 GPU 几秒钟，其他请求全部排队。Chunked prefill 把长 prefill 切成小块（chunk），与 decode 交替执行，保证 decode 请求的延迟稳定。

SGLang 中通过 `--enable-mixed-chunk` 开启。

### 3.4 Prefill-Decode 分离（PD Disaggregation）

**这道题的场景下，暂时不上。**

PD 分离把 prefill 和 decode 分到不同的 GPU 组上，各自独立扩缩容。好处是 prefill 的突发流量不会影响 decode 的延迟，decode 节点可以做更激进的 batching。

但 PD 分离需要至少两套 GPU 资源，对于"8 卡单机"的约束来说不现实。如果后续扩展到多机，PD 分离是自然的选择——代码助手场景 prefill 和 decode 的计算特征差异很大（prefill 是 compute-bound，decode 是 memory-bound），分离后可以独立优化。

### 3.5 投机解码（Speculative Decoding）

GLM-5.2 自带 1 个 MTP（Multi-Token Prediction）头，可以一次预测多个后续 token，通过验证后接受。实测可以提升 decode 吞吐 15-20%。

SGLang 中通过 `--speculative-algorithm EAGLE` 系列参数开启。但注意投机解码会增加显存占用（额外的 draft model 或 MTP 头），在显存紧张的情况下需要权衡。

### 3.6 最终推荐配置

```bash
python -m sglang.launch_server \
  --model-path zai-org/GLM-5.2-FP8 \
  --tp-size 8 \
  --context-length 262144 \
  --kv-cache-dtype fp8_e4m3 \
  --enable-mixed-chunk \
  --mem-fraction-static 0.85 \
  --host 0.0.0.0 \
  --port 8000
```

## 4. 瓶颈预判——prefill-bound 还是 decode-bound

### 4.1 理论分析

代码助手场景的典型特征：
- **长 prompt，短 completion**：输入可能是整个代码仓库（几万到几十万 token），输出通常只有几十到几百行代码
- **读多写少**：prefill 的计算量远大于 decode

对于 GLM-5.2 这种 744B MoE 模型：
- **Prefill 阶段**：需要激活 40B 参数处理所有 input token，是 **compute-bound**（算力瓶颈）
- **Decode 阶段**：每次只生成 1 个 token，需要从显存读取全部 744B 权重（实际读 40B 激活部分），是 **memory-bound**（带宽瓶颈）

在代码助手场景下，由于 prompt 远长于 completion，**整体是 prefill-bound**。

### 4.2 如何验证

没有实卡的情况下，可以用以下方法交叉验证：

1. **算力计算**：H200 的 BF16 算力约 990 TFLOPS，FP8 约 1979 TFLOPS。对于 40B 激活参数的 prefill，每个 token 约需 `2 × 40B = 80G` FLOPs（粗略估计）。256K 输入需要 `256K × 80G ≈ 20.5P` FLOPs。在 8×H200 FP8 算力下，理论 prefill 时间约 `20.5P / (8 × 1979T) ≈ 1.3 秒`。加上通信开销，TTFT 在 1.5-2 秒左右——刚好卡在 2 秒的 SLA 边界。

2. **显存带宽分析**：H200 的 HBM3e 带宽约 4.8 TB/s。Decode 阶段每 token 需要读取约 40B 参数的 FP8 权重 = 40 GB。理论 decode 时间 = `40 GB / (8 × 4.8 TB/s) ≈ 1.04 ms`。加上 KV cache 读取和计算开销，ITL 约 30-50 ms——在 100ms 的 SLA 内。

3. **公开 benchmark 交叉验证**：Lambda 的 benchmark 显示 GLM-5（FP8, 8×B200）在 8K/1K 的输入输出比下，TTFT 约 1662ms，ITL 约 103ms。B200 比 H200 快约 30-50%，所以 H200 上 TTFT 预计 2-2.5 秒，ITL 预计 130-150ms。256K 的 prefill 会更慢——**TTFT 可能是主要瓶颈**。

### 4.3 瓶颈结论

**Prefill 是瓶颈。** 256K 上下文的 prefill 延迟可能超过 2 秒 SLA。缓解措施：
- Chunked prefill 可以让第一个 chunk 的结果更快返回（但完整 prefill 仍需时间）
- 如果 SLA 严格，考虑降低上下文上限到 128K，或增加 GPU 数量

## 后记

这道面试题的精髓不在于"记住命令"，而在于两件事：

**第一，你能不能从一句模糊需求里问出约束。** 面试官说"部署 GLM-5.2"，你如果直接开始讲 TP=8，大概率已经偏了。真正的高手会先问：什么场景？什么硬件？什么 SLA？——把开放性问题收敛成可计算的问题，这本身就是工程能力的体现。

**第二，你理不理解每一个决策背后的 trade-off：**

- 为什么是 FP8 而不是 BF16？因为显存不够。
- 为什么是 TP=8 而不是 PP？因为单机 NVLink 下 TP 延迟更低。
- 为什么 KV cache 这么小？因为 MLA 把 K 和 V 压缩到 512 维的潜在空间，KV cache 只存压缩后的 `k_nope` 和 `k_pe`，注意力通过吸收优化直接在压缩空间计算。
- 为什么 `v_head_dim=256` 不影响 KV cache？因为它是 V 上投影后的维度，只影响 `w_vc` 和 `o_proj` 的计算量，不进入 KV cache。
- 为什么 AllReduce 比 AllToAll 更适合单机？因为 AllReduce 可以与计算重叠，而 AllToAll 破坏了数据局部性。EP 的真正价值在跨节点。
- 为什么 prefill 是瓶颈？因为代码助手读多写少，prefill 是 compute-bound。

如果你能把这两件事讲清楚——先反问、再推导——面试官就知道你不是在背答案，而是真正理解了推理部署的底层逻辑。

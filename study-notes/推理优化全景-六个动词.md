# 大模型推理优化,一张全景图

> 两面墙、一个仓库、一条锁链;一条公式、六个动词、一张账本。

在 H100 上跑 batch=1 的解码,GPU 算力利用率不到 1%。

不是配置错了,是物理如此:这块卡每从显存搬 1 个字节,要做约 300 次浮点运算才对得起它的算力;而解码每搬 1 个字节,只做约 1 次。推理优化的绝大多数技术,都是在跟这个 300:1 的失衡搏斗——只是它们藏在一张让人眼花的清单后面。

做推理优化,入门最劝退的就是那张技术清单:FlashAttention、PagedAttention、Radix Cache、FP8、AWQ、MLA、continuous batching、CUDA Graph、speculative decoding、torch.compile……每个名字背后都是一篇论文、一个 kernel、一套工程。我们一个个啃,啃完还是没有全局感——因为它们看起来彼此无关。

但如果退一步,只问一个最笨的问题:

> **怎么让推理更快、更省地完成?**

——更准确地说,是两个目标:**单条请求更快**(延迟),**单位硬件吐出更多 token**(吞吐)。很多技术只服务其一,这个区分后面会反复用到。

所有技术都在回答这个问题。而要把答案组织清楚,得先看清推理到底被什么卡住。答案是三样东西:**两面墙、一个仓库、一条锁链。**

---

## 一、物理图景

### 1.1 两面墙(Roofline)

GPU 跑一个算子,时间要么花在**算**上,要么花在**搬数据**上,取谁更慢。判断标准是「算术强度」——每从显存搬 1 个字节,能摊上多少次浮点运算:

- 强度高 → 撞**算力墙**(compute-bound):算不过来。
- 强度低 → 撞**访存墙**(memory-bound):数据搬不过来,算力干等。

给个量级感:H100 的 BF16 算力约 1000 TFLOPS,HBM 带宽约 3.35 TB/s,分界点(ridge point)约 **300 FLOPs/字节**——每搬一个字节,要做满 300 次运算才对得起这块卡的算力。而 batch=1 的解码本质是矩阵-向量乘(GEMV):每读一个权重字节,只做约 **1 次**乘加。1 比 300——**batch=1 时算力利用率的理论上限不到 1%**,实际系统里 decode 利用率常年在个位数徘徊。

![Roofline:两面墙与 Prefill/Decode 的位置](../infographic/inference-opt-5verbs/roofline.png)

关键洞察:**推理的两个阶段,撞的是不同的墙。**

| 阶段 | 在干什么 | 算术强度 | 撞哪面墙 |
|---|---|---|---|
| **Prefill** | 一次并行处理几千个 prompt token,权重读一次被几千个 token 复用 | 高 | **算力墙** |
| **Decode** | 一次只出 1 个 token,却要把整个模型权重 + 该请求全部 KV 搬一遍 | 极低 | **访存墙** |

还有一个贯穿全文的杠杆:**batch**。把 N 个请求的 decode 拼在一起,权重只搬一遍却服务 N 个 token,算术强度被拉高 N 倍——这是几乎所有吞吐优化的底层原理。但 batch 能开多大,取决于下面这个仓库。

### 1.2 一个仓库(显存容量)

显存里装两样东西:**权重**(固定)和 **KV Cache**(随并发和序列长度增长)。

KV 有多大?每个 token 的 KV 体积 = 2(K和V)× 层数 × KV头数 × 头维度 × 字节数。以 Llama-3-70B(GQA,8 个 KV 头)为例:2 × 80 × 8 × 128 × 2B ≈ **320 KB/token**——一条 128K 上下文的请求,光 KV 就要 **40 GB**。如果它当年用 MHA(64 头),就是 2.5 MB/token,8 倍。

容量的微妙之处在于:**它本身不是时间**。省显存不直接让任何一步变快。但它通过两条路径变现成速度:

1. **容量 → 最大 batch → 吞吐**:KV 塞得下多少并发,决定 batch 能开多大,决定访存墙下那些免费算力能被摊薄到什么程度。
2. **容量 → 缓存池大小 → 命中率**:能存多少历史前缀的 KV,决定「不算」的命中率。

所以显存不是目的,是**弹药**。这一维在很多文章里被压扁进「优化显存」四个字,但它和带宽是两种完全不同的资源——**带宽的账记在每一步的耗时上,容量的账记在我们能同时干多少事上。**

### 1.3 一条锁链(自回归串行)

第 N 个 token 必须等第 N-1 个出来才能开始——这是自回归的定义,也是延迟的物理地板。前面所有优化都只能缩短「每一环」的耗时,**没有一个能减少环的数量**。要 100 个 token,就得串行绕 100 圈。

墙决定每一步多快,仓库决定同时干多少,锁链决定至少要走多少步。三样东西,写成一条公式,就能推出全部动词。

## 二、一条公式,四类杠杆,六个动词

六个动词不是拍脑袋列的,它们从一条时间公式里推出来。一条请求的生成耗时:

```
每步耗时 ≈ max( 要算的FLOPs ÷ 有效算力 , 要搬的字节 ÷ 有效带宽 )   ← 两面墙:哪个慢听哪个
总耗时 T ≈ 串行步数 N × 每步耗时                                   ← 锁链
其中   有效算力 / 有效带宽 = 硬件峰值 P × 利用率 U
约束   权重 + 所有并发请求的 KV ≤ 显存容量 C                        ← 仓库
```

简写成一行:**T ≈ N × W / (P × U),外加一条容量约束 C**。两点说明:W(每步工作量)有两个维度——**要算的 FLOPs** 和**要搬的字节**,每步真正花掉的时间由更慢的那一维决定,这正是第一节 roofline 的公式化;容量 C 不出现在时间表达式里,它是**约束条件**——装不下就开不了那么大的 batch、存不了那么多缓存,通过这两条路间接影响 T。

要让 T 变小,数学上只有四类杠杆——**这一层是严格 MECE 的**:工作量、利用率、步数、约束,不重不漏:

| 杠杆 | 动词 | 逻辑 |
|---|---|---|
| **减少工作量 W** | 不算 / 少算 / 少搬 | W 的两个维度是要算的 FLOPs 和要搬的字节:**不算**直接删掉整段工作(FLOPs 和字节一起消失),**少算**砍要算的 FLOPs,**少搬**砍要搬的字节——删除 / 砍算 / 砍搬,互斥且穷尽 |
| **提高利用率 U** | 打满 | 硬件明明有能力,但在空转 |
| **减少串行步数 N** | 破串行 | 缩短自回归锁链决定的关键路径 |
| **放松容量约束 C** | 少占 | 不直接省时间,通过 U(batch 开大)和 W(缓存命中→不算)间接变现 |

(严格说还有第五个杠杆:提高峰值 P——换更好的卡。加钱不算优化,不在本文范围;「用好新硬件特性」如 FP8 Tensor Core,已归入少算/少搬。)

也要诚实标出 MECE 的边界:**杠杆层严格 MECE,动词层是工程近似,技术层必须用矩阵**(第三节)。动词层有两条已知的「缝」:其一,「不算」可以看作「少算」的极限形式,但机制完全不同(复用 vs 降价),分开才有操作性;其二,「破串行」的可行性依赖访存墙下的闲置算力,和「打满」共享同一个资源池——后面会看到它是「打满」的时间维度形态。这三层——**公式层(严格)→ 动词层(好用)→ 矩阵层(诚实)**——就是这套框架的完整表达。

![一条公式,四类杠杆,六个动词](../infographic/inference-opt-5verbs/framework-tree.png)

> **不算 → 少算 → 少搬 → 少占 → 打满 → 破串行**

顺序是**心法优先级**,不是实施顺序:越靠前的杠杆越便宜——省掉的计算永远比优化过的计算划算。真实系统里六个动词并联生效。

### 动词一:不算 —— 复用已有结果

最快的计算是不发生的计算。

- **KV Cache**:不带缓存,生成第 t 个 token 要把前 t 个 token 整个重新前向一遍(它们的 K/V 没存,只能重算),总量 1+2+…+n = O(n²) 次 token-前向;存下 K/V 后,每步只前向新 token,降到 O(n)。有一部分消不掉:注意力打分本身,每步仍要和全部历史 K 做点积,累计依然是 O(n²)——但单次点积只有 d 维乘加,比一次 token-前向(≈2×参数量 FLOPs)小几个量级;更重要的是它的**性质变了**:从「要重算的 FLOPs」变成「每步要读的字节」。**这是整个领域的第一笔交易——用容量和带宽,买免掉的计算**。所有推理引擎的地基,也是「仓库」和「访存墙」问题的总根源。
- **Radix / Prefix Cache**(SGLang 招牌):把复用扩展到**跨请求**。系统 prompt、few-shot 例子、多轮对话历史,这些前缀在大量请求间一模一样;用一棵基数树索引,命中就跳过整段 prefill。
- **HiCache 分层缓存**:前缀命中率的天花板是缓存池大小,而 GPU 显存里 KV 池要跟运行中的请求抢地盘。HiCache 把缓存池下沉扩容——GPU(L1)→ CPU 内存(L2)→ SSD(L3),冷前缀往下放,命中时搬回来。

这里要把 HiCache 的账算明白,因为它**表面上在「多搬」**(KV 在 PCIe 上来回倒),凭什么归「不算」?算一笔:70B 模型重算一个 4K token 的 prompt,约 2 × 70G × 4096 ≈ 5.7×10¹⁴ FLOPs,H100 上以不错的利用率跑也要**秒级**;而这段 KV 共 4096 × 320KB ≈ 1.3 GB,从主机内存搬回显存是**几十毫秒级**。差两个数量级——**花搬运,买免算,账算得过来**。当然,前提是搬运真的快:load-back 延迟一旦失控(碎片化小块传输、PCIe 争抢),这笔交易就会由赚变亏——这也是为什么 HiCache 的分层命中率和 load-back 时延必须有精细观测。

> 🍳 熬好的高汤别倒掉,下一锅接着用;冰箱塞不下,就放地窖——取的时候多走两步路,但比重新熬一锅快得多。

📍 **SGLang 源码坐标**:基数树在 `sglang/srt/mem_cache/radix_cache.py`(`match_prefix` 返回命中的前缀);分层缓存在 `hiradix_cache.py` + `hicache_storage.py`——GPU / CPU / 存储三级,代码结构和上面那笔账一一对应。

### 动词二:少算 —— 省 FLOPs

躲不掉的计算,每一次能不能更便宜?这一维有个适用条件:**只有撞算力墙时(prefill、大 batch),省 FLOPs 才是主要收益**。在访存墙下省 FLOPs,省的是本来就闲着的东西。

- **计算量化(W8A8 / FP8)**:权重和激活都降精度,矩阵乘直接跑在低精度 Tensor Core 上,算力吞吐翻倍。这才是「量化省计算」的那一半——另一半(weight-only)的账其实记在「少搬」,下一节拆。
- **稀疏注意力**:不是每个 token 都需要看全部历史。滑动窗口、StreamingLLM 只算局部注意力,把 O(n²) 的注意力计算砍成 O(n·w)。
- **MoE**:结构化的稀疏——每个 token 只激活少数专家,总参数巨大但每 token 实际算的很少。不过它在「仓库」上是**负资产**:所有专家的权重都得装在显存里,占用暴涨。这种「省算力、费容量」的交易结构,正是 MoE 部署难的根源。

> 🍳 简化配方:少放几味不影响味道的料,备料和翻炒都省。

### 动词三:少搬 —— 省带宽

decode 的主战场。访存墙下,瓶颈是搬不是算,真正救命的是**让每一步要搬的字节变少**。每步 decode 搬两样:权重,和这个 batch 里所有请求的 KV。

**砍权重搬运:**

- **Weight-only 量化(AWQ / GPTQ)**:只把权重压到 4bit,计算时再解压回 FP16 做乘法。微妙的地方在于:解量化是**额外计算**,它比不量化算得*更多*,却在 decode 下反而更快。这是「decode 慢在搬不在算」最硬的证据:多花计算换少搬字节,净赚。(顺带把量化的账彻底理清:weight-only = 纯「少搬+少占」;W8A8 = 「少算」为主、搬占兼得。「量化」从来不是一个技术,是两笔不同的交易。)

**砍 KV 搬运:**

- **KV 量化**:KV 用 int8/fp8 存,每步读一半字节。
- **MQA / GQA / MLA** 让每步要读的 KV 从根上变小——但它的主账在下一个动词,这里先记一笔交叉引用。

**砍中间结果搬运:**

- **FlashAttention / FlashInfer**:注意力的中间矩阵(n×n 的 attention score)又大又是一次性的,朴素实现要在 HBM 上写一遍再读回来。FlashAttention 用 tiling + online softmax 让整个注意力在片上 SRAM 里流水完成,中间结果**从不落显存**。同样的数学,访存少一个量级。(它救的主要是 prefill 和长序列——那里中间矩阵才够大。)
- **算子融合(torch.compile / TensorRT)**:一串小算子各自独立时,数据在 HBM 之间反复进出;融合成一个 kernel,进来一次、连算数步、出去一次。

> 🍳 别在仓库和灶台之间来回跑:一次拿齐,一气呵成,半成品别端来端去。

📍 **SGLang 源码坐标**:`sglang/srt/layers/attention/` 下光 attention 后端就有十几个文件——`flashattention_backend.py`、`flashinfer_backend.py`、`flashinfer_mla_backend.py`、`flashmla_backend.py`……一个数学定义只有几行的算子,养活了一整个目录的实现。「少搬」在不同硬件、不同 KV 布局上落地有多难、多值钱,这个目录本身就是证据。

### 动词四:少占 —— 省容量

前面说过:容量不是时间,但它是 batch 和命中率的弹药。这一维的所有技术,收益都通过「1.2 节的两条变现路径」兑现。

- **PagedAttention**:最容易被归错位置的技术——名字里带 Attention,常被当成计算优化,其实它**一个 FLOP 都不省、一个字节的必要搬运都不减**,治理的是容量**浪费**。早期系统按最大长度给每个请求预留连续显存,有效利用率只有 20%~40%;PagedAttention 借操作系统分页的思路把 KV 切成定长 block 按需分配,浪费降到 4% 以下。同样的显存,并发翻几倍——然后由「打满」把这些并发变成吞吐。
- **MQA → GQA → MLA**:注意力结构对 KV 体积的三代压缩。MQA 让所有 Q 头共享一份 KV(最狠但伤质量),GQA 分组共享(Llama-3-70B 用 8 组,8 倍压缩),MLA(DeepSeek)用低秩投影把所有头的 KV 压成一个小 latent 向量,对比 MHA 把 KV cache 砍掉 **93%**。它凭什么值得单独一格?因为它改的是**状态的体积**,收益自动兵分两路:每步读 KV 更少(→少搬),同容量塞更多请求(→打满)。**一处结构决策,三处受益**——这正是新模型清一色往这个方向走的原因。另外,它是**训练时就定死的**,推理框架只能接住,接不住(kernel 不支持)就白瞎。这一点第四节单独讲。
- **KV 驱逐 / 窗口**:StreamingLLM 式地直接丢掉远处的 KV——用精度风险换容量,是「少占」里最激进的一档。
- **Offload 的容量面**:HiCache 把 KV 下沉,同时也是在给 GPU 仓库腾地方——它同时服务「不算」(主)和「少占」(副),矩阵里会体现。

> 🍳 小份装盒 + 真空压缩:冰箱还是那个冰箱,能备下的桌数翻倍。

📍 **SGLang 源码坐标**:`sglang/srt/mem_cache/memory_pool.py` 里 `MHATokenToKVPool` 和 `MLATokenToKVPool` 两个类的对比,就是那个 93% 最直观的注脚——前者每层存全量 K/V,后者每 token 只存一个压缩 latent。同文件里的 `*KVPoolFP4` 变体,则是 KV 量化的落地。

### 动词五:打满 —— 消除空转

前四个动词决定「要算多少、搬多少、存多少」;这一维解决:硬件在这些活之间**有没有闲着**。空转有好几种,各有各的解法:

- **请求间的空转 → Continuous Batching**:静态批要等最慢的请求跑完,先结束的白占位置。连续批处理以 token 步为粒度动态进出,谁完了立刻让位,新请求马上补进——batch 常满,访存墙下的免费算力被持续摊薄。
- **阶段间的干扰 → Chunked Prefill / PD 分离**:prefill(算力墙)和 decode(访存墙)混跑会互相拖累——突然插进来的长 prefill 让所有 decode 卡一大顿,零散的 decode 又拉低 prefill 的利用率。**同一个问题,两种解法**:单机上用 Chunked Prefill 把长 prompt 切块、和 decode 均匀混批;集群上用 PD 分离干脆拆到不同的卡,各自按自己撞的墙来配硬件和 batch 策略。代价是 KV 要在 P 和 D 之间传——花互联带宽,买两边各自打满。
- **单卡装不下 → TP / PP / EP**:把权重和计算拆到多卡。本质也是打满:让每张卡都有活干,代价是引入通信(所以又需要通信/计算重叠来治通信引入的新空转)。
- **CPU 指挥跟不上 → CUDA Graph**:每个 kernel 都要 CPU 发射一次,一步 decode 几百上千次 launch;小 batch 下 CPU 发指令的速度追不上 GPU 干活的速度,GPU 反而等 CPU。CUDA Graph 把整套固定的 kernel 序列录制一次,之后一句「回放」替代上千次微管理。花的是灵活性(形状固定,得按 batch size 预录多张图)。
- **调度间隙 → Overlap Scheduler**(SGLang 招牌):上一步 GPU 在算的时候,CPU 同步准备下一步的 batch 元数据,GPU 步与步之间零等待。和 CUDA Graph 治的是**两种不同的等**:一个治 launch 开销,一个治调度开销。

> 🍳 别让灶台空着(batching);红案白案分开排班(PD 分离);别在厨师耳边一步步喊拿锅开火,教一遍流程之后喊菜名(CUDA Graph);炒这一单时同时备下一单的料(overlap)。

📍 **SGLang 源码坐标**:连续批处理的主循环在 `sglang/srt/managers/scheduler.py`(overlap 开关就在 Scheduler 初始化里);chunked prefill 是 `server_args.py` 里一个可调的 `chunked_prefill_size`;CUDA Graph 按 batch 形状预 capture 的配置在 `model_executor/cuda_graph_config.py`;PD 分离自成一个子系统——整个 `sglang/srt/disaggregation/` 目录。

### 动词六:破串行 —— 砸延迟地板

前五个动词都在优化「每一环多快」,只有这个在攻击「环的数量」。

**Speculative Decoding**:用便宜的「草稿」(独立小模型,或 Medusa 多头 / EAGLE / MTP 这类附生结构)先猜出未来 K 个 token,再让大模型**一次前向并行验证**——数学上有保证:接受的 token 分布和大模型逐个采样完全一致。猜对的部分白赚,一次前向吐好几个字,典型加速 2~4 倍。

它为什么可行?又回到两面墙:decode 撞访存墙,**验证 K 个 token 和验证 1 个,权重都只搬一遍**,多花的只是本来闲置的算力。所以破串行本质上是「打满」的时间维度形态——batching 用免费算力服务更多**请求**,spec decoding 用免费算力赌更多**未来**。

但要把丑话写进框架里:这笔交易的成本是**算力和显存**(draft 模型/额外头都要跑、要存),收益随**接受率**波动。两个必然的失效场景:一是接受率太低(草稿和目标模型分布差太远),猜错的都白验,倒贴;二是**高负载大 batch 下**,免费算力被 batching 吃光了,spec decoding 反而和正经请求抢算力——收益缩水甚至为负。所以它是低延迟场景的利器、高吞吐场景的鸡肋,**没有普适赢家**。

还有一个例子是 **MTP**(DeepSeek-V3):模型训练时就自带多 token 预测头——这是模型厂在结构层为破串行**预埋的钩子**,和 MLA 一样属于「训练时决策」。

> 🍳 猜熟客下一道要点什么,提前备着;猜对了直接上,猜错了损失一份备料。生意越忙,越没闲手玩预判。

📍 **SGLang 源码坐标**:`sglang/srt/speculative/` 目录,EAGLE 在 `eagle_worker_v2.py`,MTP 在 `frozen_kv_mtp_worker_v2.py`。最有意思的是里面还有一个 `eagle_draft_cuda_graph_runner.py`——draft 模型自己的前向也要用 CUDA Graph 消 launch 开销。**破串行的内部还嵌着打满**:动词之间的嵌套,在源码里是实打实的。

## 三、全景:一次请求的一生

看矩阵之前,先把六个动词放回**时间线**上——一条请求从到达到退场,它们在不同站点轮流上场:

```
到达 ─▶ ①前缀匹配 ─▶ ②排队进批 ─▶ ③Prefill ─▶ ④写仓库 ─▶ ⑤Decode循环 ─▶ ⑥退场
          不算         打满/少占       少算        少占     少搬/打满/破串行    │
           ▲                                                             KV 留作前缀
           └─────────────────────────────────────────────────────────────────┘
```

1. **到达 · 前缀匹配(不算)**:先查基数树,历史前缀命中就跳过对应的 prefill;GPU 缓存池里没有、但 CPU/SSD 分层里有的,拉回来接着用。
2. **排队 · 进批(打满 + 少占)**:调度器以步为粒度把它塞进当前 batch(continuous batching);长 prompt 切块和 decode 混批(chunked prefill);它的 KV 按页分配,不留碎片(PagedAttention)。集群视角下,它可能先被路由到 prefill 专属节点(PD 分离)。
3. **Prefill(少算主场)**:几千 token 并行前向,撞算力墙——低精度计算、稀疏注意力、MoE 的收益在这里兑现;FlashAttention 保证长序列不被中间矩阵拖垮。
4. **写仓库(少占)**:新产生的 KV 写进分页池;若模型是 MLA/GQA,这份 KV 天生就小;KV 量化再砍一半。
5. **Decode 循环(少搬 + 打满 + 破串行)**:每步搬权重、读 KV——weight-only 量化和 KV 量化砍字节,CUDA Graph 消 launch 开销,overlap 消调度间隙;带 draft 的系统一次验证 K 个 token。一圈一圈,直到生成结束。
6. **退场(回到不算)**:请求完成,它的 KV 不一定被丢弃——作为前缀留在缓存树上,等下一条请求命中,回到第①站。

![一次请求的一生](../infographic/inference-opt-5verbs/lifecycle.png)

这条时间线也给出了动词的**由外到内三层**:①⑥发生在**请求之间**(缓存域,管复用),②⑤的调度动作发生在**步之间**(调度域,管排布),③⑤的 kernel 动作发生在**步之内**(计算域,管执行)。复用、排布、执行——离 GPU 越近,优化越硬核;离 GPU 越远,杠杆越便宜。

### 账本:技术 × 动词矩阵

时间线管叙事,矩阵管查账。把每个技术塞进单独一格,是分类框架最容易撒的谎。真实情况是:**好技术往往一石多鸟,而且几乎都有代价格**。用矩阵才诚实:

> ● 主要收益 ○ 次要收益 ✗ 付出的代价
>
> 行序按**主收益动词**从「不算」到「破串行」排(即正文出现顺序);「决策层」一列与行序正交,训练/推理混排是有意的——**同一个动词,往往同时有训练时的结构实现和推理时的系统实现**:破串行 = MTP(训练)+ Spec Decoding(推理),少搬少占 = MLA(训练)+ KV 量化(推理)。

## 四、隐藏维度:我们能动什么?

矩阵最后一列「决策层」值得单独说。这些技术在完全不同的时间点被决定:

- **训练时(模型结构)**:MQA/GQA/MLA、稀疏注意力、MoE、MTP。模型出厂那一刻就定死了,推理工程师**选不了,只能接住**——接得住(kernel、cache 布局、调度都支持)才能吃到收益,接不住就是白纸上的数字。
- **推理时(服务系统)**:其余全部。这是推理框架的主战场,也是 vLLM / SGLang / TensorRT-LLM 竞争的地方。(严格说,AWQ/GPTQ 的量化校准发生在部署前的离线阶段,但它不改模型的结构语义,归推理侧。)

这个区分的实用价值:**看懂新模型发布**。DeepSeek-V3 选 MLA + MoE + MTP,不是三个孤立的炫技——对着矩阵看,它是在训练时一次性把「少搬+少占」「少算」「破串行」三个动词都预埋好,等于模型厂在训练时就替未来所有部署者的推理账单做了决定。反过来,推理框架的迭代(比如支持 MLA 的 attention kernel、MTP 的投机调度)本质是在**兑现训练时预埋的支票**。

## 五、判断任何新技术的三问

到这里,坐标系完整了。下次冒出任何新名词,顺着问三个问题:

1. **它省的是哪种资源?** 算力 / 带宽 / 容量 / 空转 / 串行步数——对应六个动词里的哪格?
2. **它花的是什么?** 没有白拿的优化,每一个都是交易:HiCache 花 PCIe 搬运买命中,spec decoding 花算力显存买延迟,量化花精度买算力或带宽,PD 分离花互联买两边打满,CUDA Graph 花灵活性买 launch 开销。**找不到代价格,说明我们还没看懂它。**
3. **这笔账在什么场景成立?** batch 多大、序列多长、负载多高、延迟还是吞吐优先?spec decoding 在低负载是利器、高负载是鸡肋;chunked prefill 和 PD 分离是同一问题在不同规模下的两个答案。**没有普适赢家,只有场景赢家。**

三问都答得上来,我们就不是在背技术清单,而是在读一张资源交易的账本。

## 结语

推理优化看似一堆孤立的黑魔法,底层是和一间厨房高效运转完全同构的朴素直觉:

> 熬好的高汤别倒掉,冰箱不够就放地窖(不算);配方能简化就简化(少算);别在仓库和灶台间来回跑(少搬);小份装盒真空压缩,同一个冰箱备更多桌(少占);灶台别空、红案白案分开排班、别微管理厨师(打满);闲的时候猜熟客下一道菜,提前备好(破串行)。

技术会一直翻新:FlashAttention 会有下一代,量化会有新格式,投机采样会有新变种。但「两面墙、一个仓库、一条锁链」不会变——那是硬件物理和自回归数学决定的。抓住这套骨架,新技术对我们就不再是要从头学的陌生名词,而是账本上多出来的一行:看它省什么、花什么、什么场景划算,三问问完,归档。

这,大概就是抽象分层最实在的回报。
